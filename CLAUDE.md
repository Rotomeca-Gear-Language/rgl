# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`rgl` is the compiler for the RGL language (V3), written in C# (.NET 10, `net10.0`, nullable and implicit usings enabled). RGL is **transpiled to C++**, which is then compiled by Clang (provided by the Zig toolchain in `tools/zig`, invoked as `zig c++`). Slice 0.1 (CLI, `rgl init`, `rgl.json` manifest, cache) is implemented; the build pipeline (`Build/BuildPipeline.cs`) reads, lexes, parses and binds the entry file into IR, then emits C++ to `<cache>/projets/<project>/cpp/main.cpp` and builds the executable into the project itself, `<project>/out/<profile>/<name>(.exe)` (`out/debug`, `out/release`; the cache keeps only intermediate files), with the toolchain (slices 0.2–0.4); `rgl compile` prints « Exécutable écrit dans <chemin relatif> »; `rgl exec` runs it and propagates its exit code, `--emit-cpp` stops after writing the C++. Each stage runs only if the previous one reported no error. The V0 demo works end to end. Slice 4.1 (files and imports, below) is implemented.

## Extensions (`extend`)

`extend T { const T nom: valeur; gear [pure] f(this T v, …): R { … } gear g(…): R { … } }` ajoute à un type des constantes et des gears, **pour le compilateur seulement** : le C++ ne change pas (un gear d'extension est un gear ordinaire, nom C++ `extN_f`, une constante une constante ordinaire). Décisions : comme en C#, le premier paramètre d'une méthode s'écrit `this Type nom` (contextuel, `Parameter.IsThis`) et doit être du type étendu ; `v.f(a)` est exactement `f(v, a)` (`Type.f(v, a)` marche aussi) ; un gear sans `this` et toute constante s'appellent sur le type, `T.nom` (type nommé : mold, enum, ingot — E119 sinon) ; une extension n'est permise que dans un fichier `forge: gears` (E104 dans le `.rgl` et un `forge: train`) ; **l'extension d'un type déclaré dans le même fichier suit ce type** (`Binder._typeExtensions`) : tout fichier qui voit le type voit ses constantes et ses gears, `Fichier.Type.nom` après `import Fichier;`, `Type.nom` après `import Fichier only {Type};` (un gear d'extension porte la clé `Fichier.Type::f` dans `_gears`, que `_TryFind` reconstruit) ; l'extension d'un autre type (`extend int`, `extend [int]`, un type importé) n'est vue que du fichier où elle est écrite (`ModuleInfo.Extensions`, clé `~Type::f`) ; son type doit être écrit pareil à l'appel (égalité des types) ; pas de gear générique dedans (« pas encore pris en charge »), mais `guard` et `emit` y sont permis (sans `this`, ils sont statiques : `Type.f` comme étape ou dans un pipeline — mais un train ne s'écrit pas dans un fichier gears, donc un emit d'extension n'a pas encore d'appelant) ; un gear d'extension sous un nom de type s'appelle aussi `Type.f` partout où un nom de gear est attendu (étape, `v |> Type.f`, parcours, appel) grâce à `_gears["Type::f"]` + `ModuleInfo.ExtensionKeys`, jamais par son nom seul ; un champ lambda du mold passe avant une extension du même nom, les méthodes des collections (`push`, `add`, `has`) avant toute extension. seuls les `gear` sont génériques (un guard/emit générique est « pas encore pris en charge ») ; 512 instances au plus (E115). un paramètre déduit de nombres connus à la compilation prend le premier de int, long, float, double qui les contient tous (`_NumberTypeFor`, `GenericEnvironment.Constants` : `deux(2, 3000000000)` est `long`, `deux(1, 2.5)` `float`, un flottant hors de `float` `double`), tant qu'aucun argument non constant ne l'a fixé ; sinon les constantes s'y adaptent ou c'est un conflit (E115). `new Pair {…}` sans arguments (slice 4.5b, `_InferMoldType`, appelé par `_BindMoldExpression`) : ceux du type attendu s'il est une instance du même mold, sinon déduits du type des champs donnés (même `_Infer` que les gears) ; un type écrit sans arguments (`Pair a: …`) reste E115. `_InstantiateMold`: `MoldSymbol` nommé `Pair<int, string>`, C++ `…_gN`, enregistré dans `_molds`/`_moldDeclarations`/`_allMolds` avant ses champs (récursion par `[Arbre<T>]` permise, par lui-même E073) ; `_moldInstanceArguments` sert à la déduction. `T is X` (types égaux) et `T accept X` (au moins les champs de X) sont un `IrBoolConstant` ; un `if` dont la condition n'est faite que de tests de type (`not`, `and`, `or` compris, `_IsStaticCondition`) ne lie que la branche prise. L'émetteur n'a rien de spécial : une instance est un gear ou un mold ordinaire. Codes E114–E117. Tests : `tests/rgl.Tests/Binding/GenericTests.cs`, golden `Golden/parser/generics`.

## Paramètres par défaut et `__CALLER__` (slice 4.6A)

`gear f(int a, string b: "x", string c: __CALLER__)` : la valeur après `:` est n'importe quelle expression (`Parameter.Default`, le `Span` du paramètre va jusqu'à elle, donc l'aide de signature et le survol du serveur de langage l'affichent sans code en plus). Un paramètre avec défaut vient après ceux qui n'en ont pas, ni `mut` ni `this` n'en ont, ni un train ni un opérateur (E120, `_CheckDefault`, `_RejectDefault`). Une expression est **évaluée dans le gear appelé**, comme en JS : elle lit les paramètres qui la précèdent, défauts compris (`_BindDefaults` dans `_BindGearBody`, `IrGear.Defaults`, `_bindingDefault` interdit `fail`/`done`/`as!`/guard dans un défaut même d'un guard, `_InGuardBody`) ; un gear `pure` n'a donc que des défauts purs. Les valeurs spéciales (`ParameterDefault`: `__CALLER__` nom du gear, du train ou `lambda` qui contient l'appel, `__WHERE__` `fichier:ligne:colonne` de l'appel, `__FILE__`, `__LINE__`) sont remplies **chez l'appelant** en constantes (`_OmittedArgument` dans `_BindGearCall`), `string` sauf `__LINE__` entier ; l'appelant peut toujours donner la valeur, ce qui permet à un wrapper de transmettre la sienne. Arité : `de N à M argument(s)` (E058). `IrCall.Arguments` garde la longueur du gear : un défaut-expression omis y est un `IrOmittedArgument`. C++ : un appel qui omet une expression passe par un enveloppeur `rgl_g_nom_dK` (K arguments explicites ; paramètres = ces arguments puis les valeurs spéciales omises ; il calcule les défauts dans l'ordre puis appelle le gear : `_DefaultEntries`, `_DefaultEntry`, `_CallText`), déclaré avec le gear ; sinon l'appel est direct. Un appel par variable lambda ou référence de gear n'a pas les défauts (type de fonction sans défauts : E058 avec explication). Tests : `tests/rgl.Tests/Binding/DefaultParameterTests.cs`, golden `Golden/parser/default-parameters`.

## Precasts (slice 4.6B)

`forge: precast` : un import de mold au plus et des precasts `precast Vec2 Zero { x: 0.0, y: 0.0 }` (mold importé avant le nom), `precast {string name, bool debug} Config { name: "x"; debug: false; }` (mold anonyme écrit) ou `precast Config { string name: "x"; bool debug: false; }` (mold déclaré par les champs). Parser : `_ParsePrecast` (`AST/Precasts/PrecastDeclaration`, `Values` pour les deux premières formes, `Fields` pour la troisième ; champs séparés par `;` ou `,`). `Project/FileChecks._CheckPrecastFile` : que des imports (un seul) et des precasts, un seul precast qui déclare son mold et jamais avec un import (E104) ; un precast ailleurs que dans un fichier precast est E104. Binder (`Binder.Modules.cs`, `_DesugarPrecasts`) : un precast devient `const Type nom: new Type { … }` avant `_BindDeclarations` (le type d'un precast qui déclare son mold est le mold anonyme de ses champs, E121 pour un champ sans valeur), donc il s'importe, s'exporte et se qualifie comme une constante et le C++ n'a rien de spécial ; `_CheckPrecast` : E121 si la valeur n'est pas une donnée résolue à la compilation (`_IsPrecastData` : littéraux, constantes, molds, tableaux — `[string] data: ['a', 'b']` —, dictionnaires, tuples ; un appel est refusé) ; constexpr quand le C++ le permet (`IsCompileTime`), un tableau dynamique alloue et est construit une fois au démarrage ; `Binder.Precasts.cs` `_WithoutUnusedPrecasts` : un precast que rien n'atteint (gear, lambda, valeur par défaut, train, autre precast lu) n'est pas écrit dans le C++. Serveur de langage : un precast est un symbole constante. Pas encore : l'export JSON des precasts. Tests : `tests/rgl.Tests/Binding/PrecastTests.cs`, golden `Golden/parser/precasts`.

## Match de valeurs (slice 4.7)

`match (n) { case 1, 2 |> "petit"; case eval $ > 10 |> "grand"; default |> "autre"; }` : un switch en ligne qui donne une valeur, sur tout sujet qui n'est ni une union ni un résultat (ceux-là gardent leurs bras de type, `ok`, `err`). Décisions : `case V |> expr;` (le mot `case` du switch, la flèche `|>` du match), mêmes valeurs que le switch (constantes E051, uniques E052, une variante nue sur un enum, E040 d'un autre type) et même `case eval` où `$` est la valeur ; pas de fallthrough ni de `goto` entre bras ; exhaustivité vérifiée : sans `default`, toutes les variantes d'un enum, ou `true` et `false`, sinon E082 (une condition `eval` ne prouve rien ; un `case` sur une union ou un type sur une valeur est E080). Parser : `_ParseMatchArm` lit `case` (valeurs au-dessus du pipeline, `_ParseExpression(PipelinePrecedence)`, `MatchPatternKind.Case`/`Eval`, `MatchArm.Values`/`Condition`). Binder (`Binder.Unions.cs`) : `_BindMatch` envoie un sujet qui n'est pas une union à `_BindValueMatch`, qui réutilise `_BindCaseValues` et `_BindEvalCondition` du switch (un `SwitchContext` à part, jamais dans `_switches`, donc ni `break` ni `goto` n'y visent) ; `_UncoveredValues` ; `_TypeMatch` (type commun des bras, partagé avec le match de types). IR : `IrMatchKind.Case`, `IrMatchArm.Test` (comparaison sur `IrSwitchValue`), `IrMatch.SwitchId`. C++ : la valeur est rangée dans `rgl_swN`, comme un switch, et chaque bras est un `if` sur son test (`_ArmTest`, `_MatchSubjectName`). Tests : `tests/rgl.Tests/Binding/MatchValueTests.cs`.

## Surcharge et conversions (slice 4.5)

Un mold déclare dans son corps des opérateurs et des conversions : `[pure] Type opérateur(paramètres typés) { … }` — `+ - * / % eq < > bitand bitor bitxor shl shr` (`-` aussi unaire), et les mots contextuels `implicit` / `explicit` (une conversion a un seul paramètre, du mold). Parser : `MoldOperator` (`AST/Molds`, lu par `_ParseMoldMember` quand `_AtMoldOperator` — un opérateur ou `implicit`/`explicit` suivi de `(` après le type —, pas de `;` après son bloc ; seulement dans un mold déclaré, pas dans un type anonyme).

Binder (`Binder.Overloads.cs`, décisions : chaque opérateur est un gear nommé `Mold.opérateur`, nom C++ `<Mold>_opN`, rangé sur `MoldSymbol.Overloads` (`MoldOverload`) ; les signatures sont liées par `_DeclareOverloads` juste après les molds, les corps par `_BindOverloadBodies` avant ceux des gears ; un opérateur n'est pure que s'il l'écrit (`pure Vec2 +(…)`), un appel depuis un gear pure d'un opérateur qui ne l'est pas est E057 ; pas de `mut`, pas dans un mold générique (« pas encore pris en charge »)). Déclaration invalide : E118 (nombre de paramètres, le mold n'est pas parmi les opérandes — le paramètre d'une conversion —, `eq`/`<`/`>` qui ne renvoient pas un bool, conversion vers le même type, doublon). Résolution (`_TryOverload`, appelée en tête de `_BindOperation` et de `_BindUnaryOperation` quand un opérande est un mold) : les opérateurs des molds des deux opérandes, ceux dont les paramètres sont exactement les types des opérandes, sinon ceux où chaque opérande se convertit (`_CanCoerce`, donc `v * 2` ou `v + {x: 1.0, y: 2.0}` passent) ; plus d'un est E009 ; aucun, c'est l'opération du langage (`eq` champ à champ, ou E040). L'ordre des opérandes compte, rien n'est inversé. `not eq` se déduit de `eq` (déjà `not (a eq b)`), `<=` de `<` et `eq`, `>=` de `>` et `eq` (`IrBinary Or` de deux appels ; les opérandes sont lus deux fois, un opérande avec effet est « pas encore pris en charge »). `<` sans `>` pour les mêmes opérandes, ou l'inverse : E010 (`_CheckComparisonPairs`, par mold). Conversions : `_Coerce` essaie d'abord `_FindConversion(…, "implicit")` — une conversion vers exactement le type attendu, qui passe avant le duck typing, partout où un type est attendu (déclaration, argument, retour, opérande converti) — ; `as` appelle l'`explicit` d'abord (`_BindCast`, `as` seulement, pas `as?`/`as!`), sinon une implicite. L'IR est un `IrCall` ordinaire (`_OverloadCall` : E057, `_calls`), l'émetteur n'a rien de spécial. Codes E009, E010, E118. Tests : `tests/rgl.Tests/Binding/OverloadTests.cs`, golden `Golden/parser/mold-operators`.

## C++ runtime (`runtime/`)

C++23 library (C++23 for `std::flat_map`) linked into every compiled RGL program: `include/rgl/standard/` (headers) and `src/` (implementation). `memory.hpp` — `AbiAllocator` (three C function pointers, no `std::allocator`), `default_allocator()`, and `out_of_memory()`, which aborts: the runtime never goes on with a too-small buffer or a silently emptied string. `string.hpp` — `rgl::standard::string` (immutable: ≤ 22 chars stored inline, longer ones in a heap block shared by copies with an atomic refcount, constexpr long literals as zero-copy views; `data()` is always NUL-terminated) and `rgl::standard::mstring` (mutable, inline then heap buffer growing ×1.5, never shared, keeps its allocator on copy-assignment, safe to append/insert from itself); both live in `rgl::standard::primitives` and are re-exported in `rgl::standard`. `array.hpp` — the RGL arrays, growing only at the end, elements modified only through a `mut` variable (non-const `operator[]` and `at(i, where)` in `readable`, each array giving a non-const `data()`): `array<T>` (`[T]`, heap block through an `AbiAllocator`, growth ×1.5, copy = element copy), `fixed_array<T, N>` (`[T;N]`, inline, constexpr), `bounded_array<T, Min, Max>` (`[T;N..M]`, inline storage of Max elements, `fits`, `can_push`, `from`/`try_from`), `non_empty_array<T>` (`[T+]`, `first`/`last`, `from`/`try_from`); all read through `has_index`, `operator[]` (unchecked), `at(i, where)` (stops out of range) and `try_at` (nullptr), share the `rgl_sequence` tag (written as text `[1, 2, "a"]` by `format.hpp`), and `make_array<T>(spread(a), x, …)` builds `[...a, x]` with one allocation; it needs the Memory component (`default_allocator`). `dictionary.hpp` — `dictionary<K, V>`, the RGL `[K:V]`: two RGL arrays, the keys sorted (symbols by name) and the values in the same order, searched by binary search and allocated by the runtime allocator like any array (since B.3 — it was a `std::flat_map`; it needs the Memory component), read with `at(k, where)` (stops on a missing key), `try_at`, `contains`, grown only by `add(k, v, where)` (stops on a duplicate key; `can_add`), a value replaced through a `mut` variable (non-const `at(k, where)`, `operator[]`), written as text `[k: v]` (`[:]` empty). `tuple.hpp` — `tuple<T…>`, an alias of `std::tuple`, read with `item<I>(t)` (non-const for a `mut` variable), written `(1, "a")`. `range.hpp` — `range<T>(first, last, step, exclusive, where)`, a `range_view<T>` (marked `rgl_sequence`, so arrays are built from it by `from`) computing each value on demand, counted in `__int128` so no bound overflows, empty when the step goes the other way, stopping on a zero step. All header only; `runtime/tests/array_tests.cpp` covers arrays, dictionaries and tuples. `arguments.hpp` / `src/arguments.cpp` — `read_arguments(argc, argv)`, called by the generated `main` only when the entry train takes `args`: the arguments without the program name — on Windows from `GetCommandLineW` + `CommandLineToArgvW` converted to UTF-8, since `main`'s `argv` uses the ANSI code page (link with `-lshell32`). Each `src/*.cpp` is a separately linked component (see `ZigToolchain.Components`): adding one means a new `RuntimeComponent` value and a line there. The runtime must compile without exceptions: no `throw`, even in constexpr code (use a non-constexpr `[[noreturn]]` abort helper). `mstring::to_immutable()` gives a `string`, as named in the spec. `symbol.hpp` — `rgl::standard::symbol`, the RGL `symbol`: a light handle (pointer to a unique `symbol_entry`), copied and compared (`==`, identity) like a pointer, all `constexpr`; a `§nom` literal is a generated `inline constexpr symbol_entry rgl_s_<nom>{"nom", n};` at the top of `main.cpp` (one per name, unique across the program), so literals need no allocation, no lock and no runtime source; `src/symbol.cpp` (component `Symbol`, linked only when used) holds the symbol table for names known only at run time: `symbol::intern(name, size)` (thread-safe, open addressing behind a `shared_mutex`, entries never freed, table created on first use so static-init order is safe) and `symbol::register_literal(entry)`, which a program must call for its literals before its first `intern` so both give the same identity — `runtime/tests/symbol_tests.cpp` covers it. In a template a symbol writes its name alone (`{§pret}` → `pret`), and an error its message and position (`négatif (main.rgl:3:5)`, from the generated `rgl_write`). `soa.hpp` — `soa_array<Layout>`, an array of molds stored in columns: `operator[]`/`at` rebuild an element by value (gather), `push` spreads it (scatter), `set(i, v)` puts it back in place (`Layout::store`), `columns()` and `index(i, where)` write one field in its column, `append`, `has_index`, `try_at` (nullable), `fits`/`from`/`try_from`, a by-value iterator, `==`, `rgl_sequence`, and `make_soa<Layout>(parts…)`; the other arrays' `from` and `append` read any source through `size()` and `operator[]` only, so an SoA converts to and from them; `runtime/tests/soa_tests.cpp` covers it with a hand-written Layout. `function.hpp` — `function<R(Args…)>`, the type of an RGL lambda, header only: never empty, a callable up to three pointers (nothrow-movable) stored inline, a larger one in a heap block from an `AbiAllocator` shared by copies with an atomic refcount (the callable is immutable), call through a small table of operations; `runtime/tests/function_tests.cpp` covers it. `exception.hpp` — `guarded<T, E>` (`guarded<void, E>` too), the result of a guard, `failure<E>`/`fail(error)`, `finish<T>`/`done(value)` (a success that sets `finished()`, which stops a guard loop) and `no_error`; `loop.hpp` — `repeat<T>(step, first, limit)`, the guard loop `*` (`first` forwarded, each turn's value moved out of the previous result), and its `loop_result` (`failed`, `exhausted`, `value`, `error`), header only, covered by `runtime/tests/exception_tests.cpp`; the errors themselves are structs generated by the compiler; header only. `convert.hpp` — `parse_number<T>(text, out)` and `cast_message`, for `as!`, header only. `cast.hpp` — numeric casts and bounded types, header only: `fits<To>(v)` (integer range; a float truncated toward zero, NaN never fits; to a float always), `checked_cast`, `try_cast`, `narrow_float`, `in_bounds`, `checked_bounds`, `try_bounds`; the stopping ones print « rgl : <message> (<where>) » and abort; `runtime/tests/cast_tests.cpp` covers it. `console.hpp` / `src/console.cpp` (component `Console`, linked only when used) — `console::write` (UTF-8 bytes as is when redirected, through a 16 KB buffer flushed when full, before a read, at exit and on `SIGABRT`; `WriteConsoleW` in UTF-16 on a real Windows console, whatever its code page) and `console::read_line()` (without `\n` or `\r\n`, `""` at end of input; `ReadConsoleW` on a real Windows console). `runtime/tests/exception_tests.cpp` and `runtime/tests/console_tests.cpp` (fed through stdin by `RuntimeTests`) cover them. `runtime/tests/string_tests.cpp` is a self-checking program (exit 0 on success, counting allocators detect leaks and wrong-allocator frees); `tests/rgl.Tests/Runtime/RuntimeTests.cs` compiles it with `tools/zig` (`-Wall -Wextra -Wpedantic -Werror`) and runs it as part of `dotnet test`, together with `runtime/tests/entry_tests.cpp` (its own `main` that reads and echoes its arguments, checked for UTF-8 and exit-code propagation), skipped when Zig is not installed. It is also clean under `-fsanitize=undefined` and cross-compiles for `x86_64-linux-gnu.2.28`.

### Live progress — the "atelier" (takes precedence over `contexte/`)

The user tracks progress at https://rotopi.tailda977d.ts.net/rgl-atelier (Raspberry Pi on their tailnet): spec recap, every slice with its tasks, the **decisions already taken** for "À décider" items, the current slice and the finished ones. Before starting or resuming work on a slice, read the state as JSON:

```sh
curl -s https://rotopi.tailda977d.ts.net/api/store/rgl-atelier/state
```

Shape: `current` (uid of the slice in progress, e.g. `s001`), `done` (finished uids), `versions[].slices[]` with `id` (`0.1`), `name`, `todo[]`, `decide[]` (`text`, `choice`, `decided`), `uid`. Treat it as read-only: the same endpoint accepts `PUT` of the whole state, but only write to it if the user explicitly asks (the user marks slices done and records decisions themselves in the site).

Working rules taken from the roadmap:

- **Vertical slices.** Each slice goes through the whole chain (lexer → parser → AST → IR → C++ → build) with its golden tests before moving to the next one; the compiler must work at every step.
- **"À décider" items must be settled before coding the slice.** Use the `choice` recorded in the atelier; if an item is still `decided: false`, do not silently pick an answer — ask the user.
- **No Clang error may reach the user**: any C++ compile error is a transpiler bug, not a user diagnostic.

## Intended compiler architecture (from the roadmap)

- **Lexer**: hand-written, UTF-8 (BOM tolerated), longest-match operators. Every token carries a `SourceSpan` and its trivia (whitespace, comments) for the future formatter.
- **Parser**: recursive descent, one function per grammar rule, Pratt parsing for expressions; error recovery by resynchronising on `;`, `}` and declaration keywords.
- **Diagnostics**: code (E/W number from the spec table), level, position, message, suggestion.
- **IR**: independent of C++ — all semantics are defined there (a future interpreter/JIT is meant to reuse it).
- **CppEmitter**: emits `#line` directives pointing back to the RGL sources, then calls Clang and propagates the exit code.
- **Tests**: golden files — RGL source → expected output, faulty source → expected diagnostics (and printed AST from slice 0.3). A failed run leaves `*.actual` / `*.received.*` files (git-ignored).
  Implemented for the parser in `tests/rgl.Tests/Golden/GoldenTests.cs`: every `Golden/parser/*.rgl` is lexed and parsed, and compared with `name.ast` (`AstPrinter` format) and `name.diagnostics` (one `Diagnostic.Format` line each, empty file if none). Files are read from the source tree (`[CallerFilePath]`), so on a mismatch or a missing expected file the harness writes `name.ast.actual` / `name.diagnostics.actual` next to them: review, then rename to accept. A new case is just a new `.rgl` file. The folder is forced to LF in `.gitattributes`.

Project/CLI conventions (spec §35): one `.rgl` entry file per project (no header, holds the entry train `([string] args): uint`), every other source is `.forge` with a `forge:` header. Commands: `rgl init` (`--web` creates an HTTP server and `src/Home.paper`), `rgl compile <file>`, `rgl exec <file>`, `rgl check`, options `-d <dir>` and `--emit-cpp` (stop after transpilation; called `--debug` in the spec, renamed by a slice 0.1 decision). `--emit-asm` stops after compiling the generated C++ to assembly with the profile's optimisations (`ICompilerToolchain.EmitAssembly`, `-S -g0`, Intel syntax on x86), written to `<cache>/projets/<project>/asm/<profile>/main.s`, nothing linked. Generated C++ goes to the cache: `%LOCALAPPDATA%\rgl` on Windows, `~/.cache/rgl` on Linux.

## Zig toolchain (`tools/`)

- `tools/toolchain.json` (`{ "zig": "<version>" }`) is the single source of truth for the Zig version. Everything else in `tools/` (including `tools/zig/`) is installed by the script and git-ignored; only `toolchain.json`, `fetch-tools.cs` and `tools/README.md` are tracked.
- `tools/fetch-tools.cs` is a standalone .NET 10 **file-based app**, not part of the compiler. It finds `tools/` by walking up from the current directory, reads `ziglang.org/download/index.json`, checks the SHA-256, extracts (system `tar` for `.tar.xz` on Linux) and swaps `tools/zig` atomically. - `rgl.csproj` excludes `tools/**` from compilation: otherwise the SDK's default `**/*.cs` glob would pull in `fetch-tools.cs` and fail with CS8802 (two files with top-level statements). Keep that exclusion if the csproj is reworked.

## Longueur, index négatif, opérateur `[]` (slice 4.8, début)

`.length` remplace `.len` (tableaux, dictionnaires, `string` : nombre de **caractères Unicode**, pas d'octets ; `string::length()` du runtime). `a[i]` et `s[i]` : un index négatif compte depuis la fin (`-1` = dernier) ; un index connu hors limites est E086 (`-N..N-1` pour `[T;N]`), un `[T;N]` avec index négatif connu est résolu à la compilation ; `s[i]` donne un `string` (un caractère, pas de `char` hors `unsafe`) ; hors limites : arrêt, ou échec du guard (`has_index`/`at`, `detail::resolve_index`/`resolve_rank`). Un mold déclare `pure T [P i] { … }` (lecture, gear `Mold.[]`, `this` = le mold) et `mut T [P i] { … }` (écriture, `Mold.[]=`, `this` modifiable, `value` = valeur écrite ; `m[i] <- v` exige une variable `mut`, E102 sinon ; affectation composée pas encore prise en charge) : `MoldOperator.IsMutable`, `Binder.Overloads.cs` (`_DeclareIndexer`, `_BindIndexerRead`, `_TryBindIndexerWrite`). L'ingot `index` (base `long`) est un élément du langage : `_IndexIngot` le cherche sous `std.index`, `Collections.index` ou `index` (provisoire, tant que la std n'est pas embarquée) ; dans un opérateur d'index, un entier se convertit implicitement vers `index` et vers tout entier (`IrNumericCast` contrôlé). Pas encore : std embarquée, `char` / `unsafe`.

## Std embarquée (étape 1 de la 4.8)

Les sources de la std vivent dans `std/` du dépôt (copie du projet `RGL V3/std`, `extentions/` compris ; **c'est ici qu'on les édite désormais**) et sont embarquées par `rgl.csproj` (`EmbeddedResource`, nom `Rgl.Std/<chemin>`). `Project/StdLibrary` les écrit une fois par version du compilateur dans `<cache>/std/<MVID>/`, et `SourceGraph` les range dans une portée `std` (fichiers nommés `std.Math`, boxes `std.Geometry.box`) : un `import X;` ou `import box B;` que le projet ne résout pas est cherché dans la std (le projet l'emporte), `import [..]` depuis la std reste dans la std. Pas encore : import implicite, préfixe `std.`, masquage avec avertissement, élagage (les avertissements d'un gear de la std inutilisé, comme W010 de `gcd`, remontent), lang items `std.*` (`_IndexIngot` cherche déjà `Collections.index`, nom que prend l'ingot importé).

## Extensions : fichiers `forge: extend` globaux et élagage (correction de la 4.7b)

Ce qui précède sur la visibilité des extensions est remplacé : les extensions écrites dans un fichier **`forge: extend`** (type précis, primitif, collection, générique) s'appliquent à tout le programme, sans import. `SourceGraph.Loader.LoadExtensionFiles` charge d'office tous les `forge: extend` du projet, de ses boxes et de la std (avant les autres fichiers ; un fichier d'extension et ce qu'il importe ne voient donc pas les extensions) ; `ModuleInfo.IsExtensionFile` range leurs extensions dans `_globalExtensions` / `_globalGenericExtensions` (`_VisibleExtensions`, `_VisibleGenericExtensions`). Un `extend` écrit dans un `forge: gears` reste local à son fichier (ou suit son type). Chaque `forge: extend` a donc son namespace propre (E123 : `std/collections`, `std/strings`). Élagage (`Binder.Pruning.cs`) : un gear d'extension (`_extensionGears`, instances génériques comprises) n'est écrit en C++ que si une instruction, un gear ordinaire ou un autre gear d'extension utilisé l'appelle. Tests : `ExtensionFileTests`.

## Parcours : rang, arrêt anticipé, modification sur place

- **Rang** : la lambda d'une étape de parcours prend `(x)` ou `(x, i)` ; celle d'une accumulation `(acc, x)` ou `(acc, x, i)`. Le rang est un `int` (`IrIndexValue`, `_indexValue` dans `CppEmitter.Each`) — pas un `uint`, pour que `x + i` et `-1 - i` n'élargissent pas en `long` — et ne peut pas être `mut`. Seules les lambdas écrites sur place l'ont (pas un gear ni un guard nommé).
- **Arrêt anticipé** : `done valeur;` dans la lambda d'un `|+>` arrête l'accumulation avec cette valeur (`DoneStatement.Value`, `LambdaContext.FoldType`, `IrReturn.StopsFold`) ; elle est convertie au type de l'accumulateur ; `done valeur;` ailleurs, ou `done;` dans cette lambda, est E060. Émission : la lambda met un indicateur (`_foldStop`) à vrai, renvoie la valeur, et la boucle fait `break`. Le parser lit `done` suivi d'un nom, d'un littéral, `true`, `false` ou `null` comme `done valeur;`.
- **Modification sur place** : une lambda d'étape de parcours ou d'accumulation (`LambdaContext.InPlace`) peut modifier le **contenu** (éléments, champs) des variables et paramètres `mut` qu'elle capture, et les passer à un paramètre `mut` : elle est appelée sur place, `[&]`, ce n'est pas une copie. Réaffecter la variable elle-même, `push` et `add` restent interdits (E005, E014).
- Un appel d'extension générique donne à une lambda en argument le type de paramètre du gear, une fois ceux du `extend` déduits de la valeur (`_GenericExtensionParameterTypes`) : `xs.any((x) => x > 8)`.
- `std/extentions/collections_ext.forge` : `indexOf`, `any`, `all`, `reverse`… n'ont plus de `switch`/`goto`. Un gear `pure` qui prend une lambda la déclare `pure (T) => bool`.

## La std (suite) : import implicite, `std.nom`, contenu

Tous les fichiers de la std (hors boxes) sont toujours liés, avant ceux du projet (`Loader.LoadStd`, modules `std.Math`, `std.Console`…). Chaque fichier hors de la std reçoit un import implicite : `std.nom` désigne un nom de n'importe lequel d'eux, à plat (`std.writeLine`, `std.sqrt`, `std.PI`, `std.Random` ; `Binder._ImplicitStd`, `_FlattenTools`, E103 si deux fichiers de la std déclarent le même nom) ; `import std only {writeLine, abs as valeurAbsolue};` les rend visibles tels quels ; un fichier ou un import du projet qui s'appelle `std` l'emporte ; `import Math only {…}` / `import Math;` marchent toujours (le projet d'abord, la std ensuite). Élagage : seuls les gears de la std (et les extensions) atteignables sont écrits en C++ (`_IsPrunable`). Les avertissements et notices d'un fichier de la std ne sont pas montrés (`DiagnosticBag.Add`). Un `error` qui en étale un autre ignore ses champs `message` et `where` (`Errors.forge`). Un argument qui est une constante nommée garde son type dans l'inférence d'un générique (`std.writeLine(std.PI)` écrit un double).

Contenu, tout en RGL (`std/`, tests dans `tests/rgl.Tests/StdTests.cs`) : `Console` (`write`, `writeLine`, `readLine`, `readInt`), `Math` (constantes `PI` `TAU` `E` `LN2` `SQRT2`, `abs`/`unsignedAbs`/`sign`/`min`/`max`/`clamp`/`lerp`, `floor` `ceil` `round` `trunc` `fract`, `sqrt` (Newton) `pow` `factorial` `gcd` `lcm` `hypot`, `sin` `cos` `tan` `exp` `ln` `log` `log2` `log10` `atan` `atan2` `asin` `acos` par séries), `Random` (Park-Miller : `Random.seed(n)`, `next`, `nextInt(min, max)`, `nextDouble`, `nextBool` sur un `mut Random`), `String` (constantes, `toString`), `Errors`, `Logs`, `System` (`programValue`), `Color`, la box `Geometry` ; `extentions/strings_ext.forge` (chaînes en caractères Unicode : `substring` `indexOf` `contains` `startsWith` `endsWith` `repeat` `reverse` `toUpper` `toLower` `trim*` `padStart` `padEnd` `split` `lines` `replace` `toInt` `toDouble` `isDigit`…) et `extentions/collections_ext.forge` (tableaux : `first` `last` `contains` `indexOf` `any` `all` `find` `filter` `count` `take` `drop` `slice` `reverse` (en place) `reversed` `distinct` `join` `concat` `flatten` `sum` `product` `average` `min` `max` `sorted` ; dictionnaires : `isEmpty` `getOr`). Pas encore : les erreurs standard (`Exception`, `CastError`, `LoopError`) restent déclarées par le compilateur, pas par la std ; le train d'entrée n'accepte pas encore `programValue`.

## `use <Nom>;` et fin de la 4.8

- **`use <Math>;`** importe la std : `use <Nom> [as Autre] [only {a, b as c}];` (`ImportKind.Std`, `use` contextuel suivi de `<`, `Parser._AtUse`). Il désigne **le fichier ou la box** de la std de ce nom sans le dire (`SourceGraph.Loader._ResolveStd` : un fichier de premier niveau, ou l'index de la box ; les deux à la fois est E107) ; un fichier à l'intérieur d'une box (`Private`) n'est pas visible ; `use <std>;` désigne toute la std à plat (`std.nom`, `use <std> only {…}`). **`import` ne cherche plus dans la std** : un nom de la std y est E107 avec « écris use <Nom>; » ; `import box` ne nomme que les boxes du projet (la std elle-même s'importe par `use`, sauf une box sœur dans la même box de la std). Le LSP lit la std (`ProjectContext.Std`, complétion après `use <` et `use <X> only {`, survol ; une box de la std est lue par le fichier de son nom, donc les noms venus d'autres fichiers de la box comme les constantes de `Math.box/Constants.forge` ne sont pas proposés).
- **Masquage** : un nom que l'utilisateur déclare et que `use <X> only {…}` lui donnait déjà masque celui de la std avec W015 (`_stdImportKeys`, `_ClaimName`) ; déclarer un type d'erreur standard (`Exception`, `CastError`, `LoopError`) est permis avec W015.
- **Erreurs standard** : `Exception`, `CastError` (`string item`, `typeName target` : le texte refusé et le type visé d'un `as!`) et `LoopError` sont déclarées par `std/Errors.forge` (`std.Errors.Exception`…, nom C++ `rgl_m_std_d_Errors_d_Exception`) ; `Binder.Bind` lie ce fichier **en premier dans tout programme**, même sans la std (`StdLibrary.ErrorsModule` le lit à part) et en prend les trois molds par identité (`_TakeStandardErrors`, jamais par leur nom). Le nom court et `std.Nom` y mènent tant que l'utilisateur ne déclare pas le sien (`_TryFind`). `_DeclareStandardErrors` ne sert plus que si la std est introuvable. `_StandardFailure` écrit message, where, les champs donnés puis `{}` pour les autres. Une constante de la std que rien n'atteint n'est pas écrite (`_WithoutUnusedPrecasts`).
- **Code de sortie** : `$ v` et l'emit qui termine le train d'entrée acceptent un ingot de `uint` (`programValue` de la std) sans `°`.

`Errors.forge` : l'ingot `errorCode` (base `uint`, constantes `NONE` 0, `NOT_FOUND` 404, `INVALID` 400, `IO` 5) est le code de `StandardError` (défaut 0), que `NotFound`, `ParseError` et `IoError` étalent ; `System.forge` l'y prend pour `programValue.fromCode`.

## Documentation `///` (slice 4.9)

Les commentaires `///` (exactement trois barres ; `////` reste un commentaire ordinaire) sont de la documentation XML, lue **hors du binder et de l'IR** : elle n'a aucun effet sur le typage, le flux ou le C++, et `compile` ne la lit jamais (une documentation fausse ne fait pas échouer un build). Le lexer en fait un trivia `TriviaKind.DocComment`. Décisions : `/// Texte` est le raccourci de `<summary>` (texte libre au début, jusqu'à la première ligne qui commence par une balise de section — connue ou non, hors `<c>`, `<code>`, `<para>`, `<list>`… ; `&` et `<` du texte libre sont échappés, ailleurs le XML doit être valide, `<![CDATA[…]]>` pour du code avec `<`) ; un commentaire qui commence par une balise n'a pas de résumé implicite ; résumé implicite + `<summary>` = DOC008 ; le bloc est collé à la déclaration (une ligne vide ou un `//` le détache ; un commentaire avant `export gear f()` documente le gear) ; pas de `<inheritdoc/>`, `<fails type="E">` propre à RGL, texte libre après une balise ignoré (DOC006) ; pas de `//!` de module.

Code (`Docs/`) : `DocExtractor.Before(token)` (les lignes `///`, indentation commune retirée, avec l'indice source de chaque ligne), `DocParser.Parse(block, diagnostics?)` (reconstitue un XML `<doc>…</doc>` ligne à ligne pour garder les positions, `XmlReader` sans DTD, jamais fatal : XML invalide → DOC001 et le texte brut en résumé, `IsValid` faux), `DocComment`/`DocSection` (XML intérieur + Markdown), `DocRenderer` (Markdown, fiche de survol `Hover`, `ParameterText`), `DocCollector.Collect(module, unit, tokens)` (un `DocEntry` par gear/guard/emit/train/mold/error/champ/enum/variante/ingot/constante/extend et ses membres, id `Fichier:nom` ou `Fichier:Type.membre`, signature écrite sur une ligne, `IsPublic` : un `.forge` qui exporte le nom ou n'exporte rien), `DocValidator.Validate` (DOC002 paramètre inconnu, DOC003 paramètre non décrit — notice, seulement si au moins un `<param>` est écrit, DOC004 cref non résolu, DOC005 `<returns>` sans valeur, DOC006 balise ou texte inconnu, DOC007 typeparam inconnu, DOC008 doublon, DOC010 `<fails>` sur autre chose qu'un guard/train ou type d'erreur inconnu, DOC011 nom public sans résumé — notice, DOC012 attribut manquant ; DOC009, exemples testés, n'existe pas encore), `DocExporter` (`Json`/`Xml`, format versionné `FormatVersion`). Les codes `DOCxxx` (`DocCodes`) ne s'affichent que par `rgl doc check` et ne passent pas par `DiagnosticCodes`.

CLI (`Cli/DocCommand.cs`) : `rgl doc check [fichier|-d dossier] [--strict]` lit le projet, ses imports et la std (pour résoudre les références), vérifie les commentaires du projet seulement (jamais ceux de la std) et compte les éléments documentés ; `--strict` fait échouer sur un avertissement. `rgl doc build` écrit `out/docs/api.json` et `api.xml` (fichiers du projet seulement). Éditeur : `ModuleInfo.DocumentationFor` (survol, complétion) rend la fiche Markdown d'un `///` (sinon les commentaires `//` ordinaires comme avant), `DocCommentFor` + `SignatureResult.ParameterDocumentation` donnent la description `<param>` du paramètre en cours ; la grammaire TextMate colore `///` et ses balises. Squelette : taper `///` au-dessus d'une déclaration sans commentaire propose (déclencheur `/`, `CompletionProvider._DocumentationSkeleton`, `Docs/DocSkeleton`) un snippet avec le résumé et une balise par paramètre générique, paramètre, résultat et, pour un guard ou un train, `<fails>` ; ailleurs un `/` ne propose rien. **La std est entièrement documentée en `///`** (tout nom public, champs et variantes compris) et un test (`La_documentation_de_la_std_est_sans_avertissement_ni_notice`) la relit sous un chemin hors std pour que ses DOC ne soient pas masqués : toute nouvelle déclaration de la std doit être documentée. Un gear d'un `extend<T>` peut décrire le `<typeparam>` du bloc. Tests : `tests/rgl.Tests/Docs/DocumentationTests.cs`. Les balises avancées sont notées dans l'atelier (slice 4.9). Pas encore : diagnostics `DOCxxx` dans l'éditeur, `rgl doc test`, `index.json`, site, balises avancées (`<deprecated>`, `<since>`…), `<fails>` croisé avec les erreurs du binder (DOC010 complet), génération de squelette, renommage des `name`/`cref`.

## Fichiers entiers : `raw` et `bytes` (slice 5.1a)

`var t <- raw "a.txt";` lit tout un fichier en `string` (UTF-8 strict, BOM retiré ; octets invalides = `IoError`), `bytes b <- raw "a.bin";` en octets (le type écrit — `_expected` — décide) et `valeur -> raw "a.txt";` écrit une `string` ou des `bytes`, le fichier étant créé ou remplacé (écriture directe, pas de renommage). Décisions : le chemin est une `string` relative au dossier courant ; **la lecture et l'écriture ne sont permises que dans un guard** (E060 ailleurs, comme `fail`/`as!`) et leur échec envoie une `IoError` (`std/Errors.forge` : `message`, `where`, `code` 5, `path`) dont le type entre dans `GearSymbol.Errors` (`_CollectErrors`), donc un rail ou le `fail` du train ; `bytes` est le mot-clé de type pour `[ubyte]` (`Binder._bytes`) ; `texte as bytes` (toujours possible, `IrStringToBytes`), `octets as? string` (null si pas de l'UTF-8 valide) et `octets as! string` (guard seulement, `CastError`) — `as` seul est E085 ; `file`, `json`, `xml`, `custom` restent « pas encore pris en charge » (lecture et écriture), `raw` seul reste un nom de variable (un chemin doit le suivre : `_IsReadSourceAt`).

Parser : `ReadExpression.Path` et `WriteStatement.Path` (`FileFormats`, `_IsReadSourceAt` ; après `->`, tout ce qui commence une expression est le chemin). IR : `IrReadFile` (`IsText`), `IrWriteFile`, `IrStringToBytes`, `IrBytesToString` (`IsForced`) ; `IrProgram.IoError` (`_ioError`, pris par identité dans `Errors.forge`, déclaré avec `code` et `path` sans la std). Émetteur (`CppEmitter.Files.cs`) : une lecture est une expression-instruction qui range le contenu et fait `return` de l'échec (`_IoFailure`, `_StandardFailure`), une écriture un bloc ; composant `RuntimeComponent.File` (`file.cpp`, dépend de `String`). Runtime : `file.hpp`/`file.cpp` (`read_text`, `read_bytes`, `write`, `write_text`, `write_bytes`, `message`, un `status` : ok, not_found, access_denied, invalid_utf8, failed ; Windows `CreateFileW` sur un chemin UTF-8 converti en UTF-16, POSIX `open`), `bytes.hpp` (header seul : `is_valid_utf8`, `from_string`, `is_text`, `to_string`, `try_to_string`). Tests : `tests/rgl.Tests/FileIoTests.cs`, `runtime/tests/file_tests.cpp` (`RuntimeTests`). Pas encore : `custom<M, Train>` (5.1b), JSON (5.1c), `import json` (5.1d), XML, `file` en flux, `JsonValue` (5.1e).

## `custom<M, train>` (slice 5.1b)

`var config <- custom<Config, lireToml> "a.toml";` et `config -> custom<Config, versToml> "a.toml";` : `train` est un gear ou un guard (nom simple ou qualifié) ; en lecture il reçoit les `bytes` du fichier et renvoie `M`, en écriture il reçoit `M` et renvoie des `bytes`. Décision : ce n'est **que du sucre** pour un appel ordinaire — le binder lie `train(<lecture>)` (`_BindCustomTrain`, qui range l'argument déjà lié dans `_pathOverrides` sous un `NameExpression` factice et lie un `CallExpression`), donc arité, types (E003 : le train reçoit des `bytes`, renvoie un `M` / des `bytes`), inconnu (E035), propagation des erreurs d'un train guard (union avec `IoError`, rail ou échec du train) viennent des règles des appels ; comme `raw`, seulement dans un guard (E060). L'IR et l'émetteur n'ont rien de nouveau : un `IrCall` autour d'un `IrReadFile` (lecture) ou d'un `IrWriteFile` (écriture). Parser : `AST/InputOutput/CustomFormat` (type et nom du train), `ReadExpression.Custom`, `WriteStatement.Custom`, `_ParseCustomFormat` ; `custom` est une lecture dès qu'un `<` le suit. `custom` sans `<M, train>` est E030. Tests : `FileIoTests` (région custom). Pas encore : un train nommé (`forge: train`) comme train de `custom` n'a pas été essayé.

## JSON (slice 5.1c)

`Config c <- json "a.json";`, `var c <- json<Config> "a.json";`, `var p <- json<{int x, string nom}> "a.json";` (mold anonyme) et `c -> json "a.json";` (`json<T>` en écriture convertit la valeur en `T` d'abord). Décisions (celles de l'atelier, sauf les écarts notés) : le type lu est celui des chevrons, sinon celui de la déclaration, sinon E001 — un `json` sans type donne un mold anonyme **seulement** par `json<{…}>`, le JSON n'ayant aucune forme connue à la compilation ; dans un guard seulement (E060) ; un champ en trop est ignoré et un champ absent prend le défaut du mold (`null` pour un nullable), sinon erreur — **l'avertissement « champs en trop ou en moins » de l'atelier n'est pas fait** (rien ne le montrerait à l'exécution) ; un entier JSON (sans point ni exposant, qui tient dans un int64/uint64) se lit dans un type entier (« l'entier ne tient pas dans un T » sinon, un nombre à virgule n'est pas un entier), n'importe quel nombre dans un flottant ; une borne `int<0..100>` violée, un type qui ne convient pas, un champ manquant, une variante d'enum inconnue, une taille de tableau refusée et un JSON invalide sont une `ParseError` (`message` « $.chemin[1].y : attendu int, reçu une chaîne », `input` le chemin de la valeur, `code` 400) ; un fichier absent est une `IoError` ; le guard a donc `IoError | ParseError` dans ses erreurs (`_CollectErrors`). Écriture : indentée de deux espaces, un membre ou un élément par ligne, `\n` final, champs dans l'ordre du mold, dictionnaires par clés triées, flottants les plus courts qui se relisent (`2.0`), `NaN` et l'infini sont une `ParseError`. Forme en JSON : bool, entiers, flottants, `string`/`mstring`, nullable, mold (nommé ou anonyme, récursif par un tableau), enum (par le nom de la variante), ingot (sa base), tableaux de toute sorte, dictionnaire à clés `string`, tuple (tableau) ; lambda et symbole refusés (E040), union, résultat et autres clés « pas encore pris en charge » (`_JsonProblem`).

Pas de réflexion en C++ : l'émetteur écrit une fonction par type lu ou écrit (`CppEmitter.Json.cs` : `rgl_jr_N` lit un `json::value` en `nullable<T>`, `rgl_jw_N` écrit dans une `mstring`, mémorisées par type — `_JsonKey` —, déclarées d'avance puisqu'elles s'appellent en cercle, écrites après les constantes du fichier), qui appelle celles des champs ; le chemin se construit pendant la descente (`json::context`). Les défauts des champs viennent de `IrProgram.FieldDefaults` (les `_defaults` du binder). IR : `IrReadJson`, `IrWriteJson`. Runtime : `json.hpp` (`value` : arbre neutre, `context`, `read_*`/`write_*`, `read`/`write_file`) et `json.cpp` (composant `Json`, dépend de `String` et `File` ; analyseur récursif, profondeur maximale 256, `\uXXXX` et paires de substituts, entiers en uint64 + signe) ; `runtime/tests/json_tests.cpp` (dont 30 000 documents abîmés au hasard) ; tests de bout en bout : `tests/rgl.Tests/JsonTests.cs`. Pas encore : taille maximale d'un fichier, JSON dans un dictionnaire à clés non `string`, union et résultat, `import json` (5.1d).

## `import json` (slice 5.1d)

`import json settings;` (ou `import json settings as cfg;`) lit `settings.json` **à la compilation** et le donne en constante `settings` (`cfg`). Décisions (celles de l'atelier : le C# lit et émet des constantes, le fichier se trouve par son nom comme un `.forge`) : le fichier est cherché **par son nom** dans le projet — sous-dossiers compris, dossiers cachés et `exclude` écartés, une box ne voit que ses fichiers — et deux `.json` de même nom sont E107 *à l'import* (pas avant : `package.json` n'a pas à être unique), la casse compte ; l'import n'est permis que là où une constante l'est — le `.rgl` d'entrée et `forge: gears`, `train`, `extend` (E104 ailleurs) ; le type est déduit du contenu, pas écrit : un objet dont toutes les clés sont des noms RGL est un **mold anonyme**, sinon un dictionnaire `[string: V]` (les valeurs doivent avoir un type commun) ; un tableau est un tableau ; un entier JSON (sans point ni exposant, qui tient dans un `long`) est un entier, tout autre nombre un `double` ; `null` et un tableau vide n'ont pas de type : refusés, avec le chemin de la valeur ; un objet vide est un mold sans champ ; un JSON invalide est signalé avec sa ligne et sa colonne ; `import xml` et `import file` restent « pas encore pris en charge ».

Réalisation : `Project/JsonConstants` écrit le contenu en **texte RGL** (`var settings: {nom: "x", niveaux: [1, 2]};`, sur plusieurs lignes) que le chargeur analyse comme n'importe quelle déclaration — le binder déduit donc le type comme pour une valeur écrite à la main, et ses erreurs de typage (éléments sans type commun) pointent vers ce texte, dans le fichier de données. `SourceGraph.Loader._ExpandData` remplace l'import par `AST/Files/DataConstant` (la déclaration `const var`), avant de charger les imports : le binder ne voit jamais `ImportKind.Json`. `Binder._DesugarPrecasts` range cette constante parmi celles des precasts : donnée résolue à la compilation (constexpr quand le C++ le permet) et **écrite seulement si le programme la lit** (`_WithoutUnusedPrecasts`). Un fichier de données modifié est relu à chaque compilation (rien n'est mis en cache) ; l'éditeur ne suit pas encore ces constantes (pas de complétion ni de survol de `settings.…`, et un `.json` modifié ne relance pas l'analyse d'un document ouvert). Tests : `tests/rgl.Tests/ImportJsonTests.cs`.

## XML (slice 5.1e, première partie)

`XmlNode n <- xml "a.xml";`, `n -> xml "b.xml";`, `var c <- xml<lireConfig> "a.xml";` / `c -> xml<versXml> "b.xml";` et `import xml layout;`. Le nœud est le mold `XmlNode` de la std (`std/Xml.forge`, `forge: mold`, `use <Xml> only {XmlNode};` ou `std.XmlNode`) : `string name` (la balise telle qu'écrite, préfixe d'espace de noms compris), `[string:string] attributes` (rangés par nom ; `xmlns:x` y est un attribut ordinaire), `[XmlNode] children` (les éléments fils, dans l'ordre), `string text` (le texte écrit directement dans l'élément, entités et CDATA décodés, vide s'il n'y a que des espaces entre les fils). Décisions de Claude, **à faire valider** (l'atelier ne disait rien du détail) : pas de DTD — une balise `DOCTYPE` est refusée (pas d'entité externe ni d'explosion d'entités) ; seules les cinq entités prédéfinies et les références numériques ; commentaires et instructions de traitement (dont `<?xml?>`) ignorés ; les espaces de noms ne sont pas résolus (un nom garde son préfixe) ; l'ordre entre le texte et les fils d'un élément n'est pas gardé, ni l'ordre des attributs ; l'écriture est indentée de deux espaces, précédée de `<?xml version="1.0" encoding="UTF-8"?>`, un élément vide s'écrit `<a/>`, un nom de balise ou d'attribut qui n'en est pas un est une `ParseError` ; `xml<train>` (le nom du train s'écrit entre les chevrons, comme un `NamedType`) est, comme `custom`, un appel ordinaire du train (`_BindCustomTrain`) : en lecture il reçoit le `XmlNode` et renvoie ce qu'on lit, en écriture il reçoit la valeur et renvoie un `XmlNode` — il n'y a pas de correspondance automatique mold ↔ XML ; dans un guard seulement (E060), `IoError | ParseError` dans les erreurs (`message` « XML invalide, ligne L, colonne C : … », `input` le chemin du fichier, `code` 400). `import xml layout;` (`ImportKind.Xml`) se comporte comme `import json` (même chargeur, `FileScope.XmlFiles`, même règle de nom unique à l'import, même élagage) : `Project/XmlConstants` (System.Xml, DTD interdite) écrit un texte RGL `var layout: new std.XmlNode {name: …, attributes: […], children: […], text: …};` que le binder lie comme un precast.

Réalisation : le runtime lit en un arbre neutre (`xml.hpp`/`xml.cpp`, composant `Xml`, dépend de `String` et `File` : `xml::element`, `parse`, `serialize`, `read`, `write_file`, profondeur maximale 256) ; l'émetteur écrit deux fonctions seulement si le programme en a besoin (`CppEmitter.Xml.cs` : `rgl_xml_to_node` et `rgl_xml_from_node`, qui passent de l'arbre au struct du mold et inversement, les champs repérés par leur nom). `Binder._xmlNode` prend le mold par identité quand `std.Xml` est lié (`IrProgram.XmlNode`, `null` sans la std : `xml` est alors « pas encore pris en charge »). IR : `IrReadXml`, `IrWriteXml`. Tests : `tests/rgl.Tests/XmlTests.cs`, `runtime/tests/xml_tests.cpp` (dont 30 000 documents abîmés au hasard). Pas encore : le format `file` (flux ouvert — qui le ferme n'est pas tranché dans l'atelier), `-> xml` d'un mold autre qu'`XmlNode` sans train.

## `file` : le flux ouvert (slice 5.1e, fin)

`var f <- file "a.txt";` ouvre en lecture, `file<write>` crée ou remplace, `file<append>` écrit à la fin ; le type est `FileStream` (`PrimitiveKind.FileStream`, nom reconnu par `_BindType` comme `bytes`). Décisions de l'utilisateur : **les deux** — le flux se ferme tout seul quand sa dernière copie disparaît (fin du bloc, `undefine`) et tout de suite par `f.close()`, pour toutes les copies ; il peut lire des lignes et écrire du texte ou des octets. Décisions de Claude, **à faire valider** : `f.readLine()` (`string?`, `null` en fin de fichier ; UTF-8 strict, `\n` ou `\r\n` retiré, un BOM n'est pas retiré), `f.readBytes(n)` (`bytes`, jusqu'à `n`, aucun en fin de fichier), `f.write(texte)` et `f.write(octets)` (écrit à la suite, sans tampon) et `f.close()` ; une copie (`var g: f;`) partage le même fichier et la même position ; tout sauf `close` dans un guard (E060), où un échec est une `IoError` (`message` : fichier introuvable, « le flux est fermé », « le flux n'est pas ouvert pour cette opération » — lire un flux d'écriture ou l'inverse —, texte non UTF-8 ; `path` : le chemin donné à l'ouverture) ; `const` d'un flux avertit (W016) ; un flux n'a pas d'écriture en texte (`{f}` est E040) ; `x -> file chemin` (copier un flux) n'est pas pris en charge ; `file<read>`, `<write>`, `<append>` sont des noms lus comme un `NamedType` (`CustomFormat.Type`), un autre est E030.

Réalisation : `rgl::standard::file::stream` (`file.hpp`/`file.cpp`, même composant `File`) est un `std::shared_ptr` sur un état (chemin, mode, descripteur natif, tampon de 64 Ko pour la lecture) qui se ferme à la destruction ; `open`, `read_line`, `read_bytes`, `write`, `close` rendent un `status` (`closed` et `wrong_mode` s'ajoutent à ceux de `raw`) ; `undefine` d'un flux le remplace par un flux vide (`holdsMemory`). Binder (`Binder.Streams.cs`) : `_BindFileOpen` (`IrOpenFile`, `FileOpenMode`), `_BindFileOperation` (`IrFileOp`, `FileOperation`), appelée depuis `_BindCall` quand le nom de la méthode est `readLine`/`readBytes`/`write`/`close` **et** que la cible est une variable ou un paramètre `FileStream` (`_IsFileStream` ne regarde que les noms, pour ne pas lier la cible deux fois et laisser les extensions du même nom aux autres types). Émetteur (`CppEmitter.Streams.cs`) : des expressions-instructions comme `raw`. Tests : `tests/rgl.Tests/FileStreamTests.cs`, `runtime/tests/file_tests.cpp`.

## `spawn` : les processus enfants (slice 5.2)

`spawn "make" "-j4";`, `var r: spawn("timeout=5000,cwd=./build") "make";` lancent un exécutable, attendent sa fin et donnent un `ProcessResult ! SpawnError` (`std/Process.forge`, `use <Process> only {ProcessResult, SpawnError};` : `int exitCode`, `string stdout`, `string stderr` ; `SpawnError` : `SpawnFailure kind` — `ExecNotFound`, `PermissionDenied`, `Timeout`, `IoError` — et `string message`). `spawn` est déjà un mot-clé du lexique (`SpawnKeyword`). Décisions de Claude, **à faire valider** (l'atelier n'avait aucune décision pour cette slice, et la spec écrit un rail `!> SpawnError |> f` qui n'existe plus) : le résultat se lit comme tout résultat (`match` avec `ok`/`err`, `??`) ; chaque élément est une **chaîne** — littéral, template ou variable `string` (E003 pour un nombre), jamais un drapeau nu (E030 : `"-j4"`) ; `spawn` n'est qu'une instruction ou la valeur d'une déclaration, d'une affectation ou d'un `return` (`_spawnAllowed`, consommé par la prochaine expression liée, comme `_expected`), jamais un argument ni une étape de pipeline (E124) ; pas dans un gear `pure` (E066) ni au niveau du fichier (E053) ; pas réservé aux guards : un échec est une valeur, pas un `fail` ; **W060** quand l'instruction ignore le résultat (sa suppression par `[ignore-error]` attend les annotations, slice 5.3) ; un exécutable `rgl`/`rgl.exe` écrit en littéral est E124 et, à l'exécution, `PermissionDenied` (« un programme RGL ne relance pas rgl ») ; l'attente est synchrone (l'asynchrone coopératif est la slice 5.5, `@async` et `await`, `spawnAsync` y est prévu) ; pas de kits (E061 viendra avec eux). Options : une chaîne **littérale** entre parenthèses, `clé=valeur,clé=valeur` (une valeur entre guillemets peut contenir une virgule) : `timeout` (ms, 0 = aucun), `cwd`, `env` (`"A=1,B=2"`), `stdin` (`null` par défaut — entrée vide —, `none` — pas d'entrée —, `pipe` « pas encore pris en charge »), `stdout` et `stderr` (`pipe` par défaut, `inherit`, `null`) ; une clé inconnue ou en double, une valeur invalide : E124. Un octet de sortie qui n'est pas de l'UTF-8 devient U+FFFD (sous Windows, `cmd` écrit dans la page de code OEM : ses accents ne sont donc pas de l'UTF-8).

Réalisation : `AST/Expressions/SpawnExpression` (options, éléments), `_ParseSpawn` (`Parser.Spawn.cs`) ; `Binder.Spawn.cs` (`_BindSpawn`, `_BindSpawnOptions`, `_BindStatementValue`, `_BindExpressionStatement`) ; `IR/Expressions/IrSpawn` (`SpawnOptions`, `SpawnInput`, `SpawnOutput`) ; `Binder._processResult`/`_spawnError` pris par identité quand `std.Process` est lié (sans la std : « pas encore pris en charge ») ; `CppEmitter.Process.cs` : une expression-instruction qui lance `rgl::standard::process::run` et fabrique le `result::ok(ProcessResult{…})` ou `result::err(SpawnError{kind, message})`. Runtime : `process.hpp`/`process.cpp` (composant `Process`, dépend de `String`) — Windows : `CreateProcessW` (ligne de commande citée comme `CommandLineToArgvW`, environnement en bloc, tubes lus par sondage `PeekNamedPipe` sans thread, `TerminateProcess` au délai) ; POSIX : `fork` + `execvp`, un tube d'erreur de l'exec (`errno` → `ExecNotFound`/`PermissionDenied`), `poll`, `kill(SIGKILL)` au délai (compile pour `x86_64-linux-gnu.2.28` sous `-Werror`, mais n'a été exécuté que sous Windows). Tests : `tests/rgl.Tests/SpawnTests.cs` (lance `zig`, `cmd`/`sh`, `ping`/`sleep`), `runtime/tests/process_tests.cpp`.

## Annotations et métadonnées (slice 5.3)

`@deprecated("message")`, `@tap(…)` et `[clé, clé: valeur]` s'écrivent **devant** une déclaration (gear, guard, emit, mold, error, enum, ingot, constante ; plusieurs, dans n'importe quel ordre, après un `export` aussi). La liste des annotations est fermée : `@deprecated` et `@tap`, plus `@async`, `@sync` et `@fire`, reconnues mais « pas encore prises en charge » (slice 5.5) ; toute autre est E125. Les métadonnées sont ignorées par le compilateur (elles restent dans l'AST pour les outils) ; toute clé est acceptée. Un `[` est des métadonnées quand son `]` est suivi d'une annotation, d'autres métadonnées ou d'un mot de déclaration : `[int] nombres: …` reste une déclaration typée (`Parser._AtMetadata`). Décisions de Claude, **à faire valider** (l'atelier n'en notait aucune) : `@deprecated` ne se pose que sur un gear (guard, emit compris) et son message est un littéral chaîne (E125 sinon) : chaque appel, chaque nom pris comme valeur, avertit (W061) avec ce message, sauf depuis un gear lui-même obsolète ; `@tap` ne se pose que sur un gear ou un guard — pas un emit, pas un gear `pure` (un tap a un effet), E125 —, et « pas encore pris en charge » sur un gear générique ou à paramètre `mut`/`this` ; `before` s'exécute avant le gear et `$` y est son premier paramètre (E048 sans paramètre), `after` (par défaut) s'exécute ensuite et `$` y est la valeur renvoyée (E048 pour un gear void) ; les taps s'exécutent de haut en bas, un `before` écrit après un `after` avertit (W062) ; le corps d'un tap est une écriture `valeur -> cible`, un appel ou une lambda, sans `;` (un tap peut appeler un guard : ses erreurs sont celles du gear) ; une lambda implique `closure`, une lambda sans paramètre est simplement appelée, les autres reçoivent `$` (après) ou les paramètres du gear (avant) ; un guard qui échoue n'exécute pas ses taps `after` ; les taps ne changent jamais la valeur. `Binder.Pruning.ScanGear` parcourt aussi les taps afin de conserver les gears génériques de la std et les extensions qu'ils appellent.

Réalisation : `AST/Notes/DeclarationNotes` (`DeprecatedAnnotation`, `TapAnnotation`, `OtherAnnotation`, `MetadataBlock`, `MetadataEntry`), attachée à la déclaration par un paramètre `Notes` en fin de `GearDeclaration`, `MoldDeclaration`, `EnumDeclaration`, `IngotDeclaration` et `VarDeclaration` ; `Parser.Notes.cs` (`_ParseNotedDeclaration` ; la boucle du premier niveau est devenue `_ParseTopLevelItem`) ; `Binder.Notes.cs` (`_DeprecationOf` → `GearSymbol.Deprecation`, `_WarnDeprecated` dans `_BindGearCall` et la référence d'un gear, `_BindTaps` dans `_BindGearBody`, `_tapValue` consulté par `_BindDollar`, `_CheckNotes`) ; IR `IrGear.Taps` (`IrTap`), `IrTapValue` ; émetteur : avec des taps le corps devient la lambda `rgl_tap_body` (`[&]() -> R`), les taps avant s'écrivent d'abord, puis `auto rgl_tap_result = rgl_tap_body();`, les taps après lisent `rgl_tap_value` (le résultat, ou `value()` pour un guard qui n'a pas échoué) et `return rgl_tap_result;` (`CppEmitter.Gears.cs`). Tests : `tests/rgl.Tests/AnnotationTests.cs`, golden `Golden/parser/annotations`. Pas encore : la suppression de W060 par `[ignore-error]` (le seul usage des métadonnées par le compilateur, que la spec évoque), `@deprecated` sur les autres déclarations, les métadonnées dans l'éditeur (survol, documentation).

## Durées (slice 5.4, première partie)

`100ms`, `1.5s`, `2min`, `1h` (`DurationLiteral`) et le type `duration` (`PrimitiveKind.Duration`, mot-clé `duration`) : un entier 64 bits signé de **millisecondes**. Décisions de Claude, **à faire valider** (l'atelier ne disait rien) : un littéral doit faire un nombre entier de millisecondes (`1.0005s`) qui tient dans 64 bits, sinon E126 ; `duration ± duration`, `duration ± entier` et `entier ± duration` (l'entier compte des millisecondes), `duration * entier` et `entier * duration`, `duration / entier`, `-duration`, comparaisons et `eq` ; `as` : `d as int` (et tout type numérique, `as?`/`as!` compris) lit les millisecondes comme un cast depuis `long` (`IrDurationMilliseconds`), `n as duration` et `n as! duration` les convertissent d'abord en `long` (contrôlé) puis font une durée (`IrDurationOf`), `as? duration` est E085 ; `duration / duration` donne un `long` (les fois qu'elle tient, tronqué : `d / 1s` = secondes entières) ; pas de `%`, pas de flottant ni de `ulong` comme millisecondes sans `as` (E040), `ulong` refusé comme facteur ; division par un zéro connu E047 ; un débordement ou une division par zéro arrête le programme dans tous les modes (pas de roulement) ; écrite en texte par ses millisecondes (`5000ms`) ; pas encore en JSON, ni comme clé de dictionnaire. Binder : `Binder.Durations.cs` (`_BindDuration`, `_BindDurationOperation`, appelée dans `_BindOperation` avant l'unification) ; IR : `IrDurationConstant`, `ConstantFolder.DurationValue` ; C++ : `runtime/include/rgl/standard/duration.hpp` (classe `duration`, opérateurs constexpr, header seul), `format.hpp` l'écrit ; `_MayOverflow` ignore une opération sur durées (ses opérateurs contrôlent). Tests : `tests/rgl.Tests/Binding/DurationTests.cs`. Reste de la 5.4 : regex (CTRE, décidé), `dyn_enum` mis de côté par l'utilisateur, dates à décider.

## Regex (slice 5.4, deuxième partie)

`regex r: /motif/flags;` : le type `regex` (`PrimitiveKind.Regex`, mot-clé `regex`) et le littéral `/motif/flags`, moteur **CTRE** (décidé dans l'atelier ; `runtime/third_party/ctre/ctre.hpp`, v3.11.0, licence Apache 2.0, téléchargé de GitHub, ajouté au compilateur par `-isystem` dans `ZigToolchain` — programme et assembleur — et dans `ZigBuild.Compile` des tests). CTRE compile le motif en code C++ : **une regex ne s'écrit qu'en littéral**, jamais construite d'un texte connu à l'exécution. Décisions de Claude, **à faire valider** (l'atelier ne disait que « type natif, `regex test: /yolo/g;` » et CTRE) : flags `g` (toutes les occurrences pour `find` et `replace`, sinon la première), `i` (casse, ASCII seulement) et `m` (`^`/`$` sur chaque ligne, et `.` qui ne passe plus les fins de ligne : sémantique de CTRE) ; pas de `s` ; quatre méthodes, `r.test(s)` (`bool`), `r.match(s)` (`[string]?` : le texte trouvé puis chaque groupe, `""` pour un groupe qui n'a pas participé, `null` sans occurrence), `r.find(s)` (`[string]`), `r.replace(s, par)` (`string`, `$0` à `$9` et `$$` dans `par`) ; une regex ne se compare pas (E040) et ne s'écrit pas en texte ; pas dans un JSON. Le texte est lu en UTF-8 (`.` et `[é-ü]` voient un caractère Unicode) ; `\w`, `\d`, `\s` et le flag `i` ne connaissent que l'ASCII. `match` (mot-clé) est accepté comme nom de méthode après un point (`Parser._ParsePostfix`).

`Binding/RegexSyntax` vérifie le motif avant l'émission (E127, jamais une erreur de Clang) : la liste de ce qui est accepté est dans sa documentation — caractères, `.`, `^`, `$`, classes `[…]` (intervalles, `[:alpha:]`), échappements (`\d \w \s \b \xHH \uHHHH \1`…, `\p{…}` refusé), groupes (`(?:` `(?<nom>` `(?>` `(?=` `(?!` `(?<=` `(?<!`), répétitions (`* + ? {n,m}`, paresseuses, possessives, au plus 1000) ; il est un peu plus strict que le moteur, et un test compile tous les motifs acceptés du corpus avec CTRE (`RegexTests.Tout_motif_accepte_se_compile_avec_le_moteur`) : tout nouveau motif accepté doit y être. Binder : `Binder.Regex.cs` (`_BindRegex`, `_SyntacticType` — le type d'une cible de méthode lu sans la lier : littéral, nom, champ, élément —, `_BindRegexOperation`, appelée par `_BindCall` quand la méthode est `test`/`match`/`find`/`replace` sur une cible regex) ; IR : `IrRegexConstant`, `IrRegexOp` (`RegexOperation`). C++ : `runtime/include/rgl/standard/regex.hpp` (`rgl::standard::regex` : quatre pointeurs de fonctions, copiable, constexpr ; `make_regex<Re, Global>()`), un struct `rgl_re_N` par motif et flags (`CppEmitter.Regex.cs`, `first` = `ctre::search<u8R"rgl(…)rgl">`, `all` = `search_all`), écrit avant le code ; `regex.hpp` demande les composants String et Memory. Tests : `tests/rgl.Tests/Binding/RegexTests.cs`, `runtime/tests/regex_tests.cpp` (`RuntimeTests`). Pas encore : le flag `s`, `\p{…}`, une regex construite à l'exécution, `eq` entre regex, les erreurs de motif de l'éditeur sous le curseur exact.

## Dates (slice 5.4, troisième partie)

Le type `datetime` (`PrimitiveKind.DateTime`, mot-clé `datetime`) : un instant **en UTC**, en millisecondes depuis 1970-01-01T00:00:00Z sur 64 bits signés, comme `duration`. Décisions de l'utilisateur : un seul type, **pas de littéral** (ISO 8601 par la std), `now()` en UTC seulement, **sans fuseau** (un décalage s'écrit avec une durée : `d + 2h`). Opérations (`Binder.Durations.cs`, `_BindDateTimeOperation`) : `date ± durée`, `durée + date`, `date - date` (une durée), `< > <= >=` et `eq` entre deux dates ; jamais un entier (E040 : `d + 5` n'existe pas, écris `d + 5ms`) ; `d as long` / `d as int`… lit les millisecondes depuis 1970 et `n as datetime` / `n as! datetime` en fait une date (`IrDateTimeOf` ; `as? datetime` est E085 ; `_DurationCast`) ; une date nullable passe par l'opération générique (`eq null`). Écrite en texte en ISO 8601 UTC (`{d}`, `d as string`) : `2026-10-24T10:30:00Z`, `.mmm` si les millisecondes ne sont pas nulles, une année hors de 0000–9999 avec son signe sur six chiffres (`format.hpp`, `detail::civil_from_days`). ## Cycle de vie : `mold Handle -> fermer` (slice A1.1)

`mold Handle -> fermer { int id; }` : le gear de fin `fermer` s'appelle tout seul quand une valeur du mold sort de portée (fin de bloc, `undefine`, remplacement par une affectation, échec d'un guard, fin du train). Le contrat (`forge: contract`) en est sorti : c'est la slice P.1 de l'atelier, après le gel. Décisions de l'utilisateur (atelier) : une valeur à cycle de vie est **move-only** (copie interdite) ; le gear de fin s'appelle **une seule fois, chez le nouveau propriétaire** d'une valeur déplacée ; le gear de fin **ne peut pas échouer** (un gear ordinaire, E135 pour un guard, un emit, un train, un gear asynchrone). Choix de Claude, **à faire valider** : la syntaxe (`-> nom` après le nom du mold, pas `: T -> train` de la spec, le « train » de fin étant un gear) ; le gear de fin reçoit la valeur par référence (`gear fermer(Handle h): void`, sans `mut`, E135 sinon) et n'est jamais déplacé ; un mold qui contient un champ à cycle de vie en a un lui-même, sans gear de fin à lui (ses champs se ferment dans l'ordre inverse) ; pas dans un mold générique (« pas encore pris en charge »).

Copie (E136, `Binder.Lifecycle.cs`, `_NoCopy`) : ranger dans une variable, une affectation, un champ de mold ou un retour la valeur d'une variable, d'un paramètre, d'un champ ou d'un élément — un « lieu », `_IsPlace` — la copierait ; elle se **déplace** (`b:: a`, `b <-| a`, une variable locale seulement) ; une valeur calculée (appel, valeur `{…}`) passe. `return nom;` d'une variable locale non constante déplace d'elle-même (`_NoCopyOnReturn`), un paramètre non (il appartient à l'appelant), `done` qui rendrait le premier paramètre non plus, et `...` d'une valeur à cycle de vie non plus. Passer la valeur à un gear (argument, étape de train) ne copie pas : les molds sont reçus par `const&`. Pas encore pris en charge (E137) : une constante de ce type, un tableau, dictionnaire, tuple, nullable, union, résultat, promesse ou type de fonction qui en contient (`_BindType` enveloppe `_BindTypeCore`, `LifecycleRules.HoldsInside`), une lambda qui en capture une, un point de reprise `^N` devant une étape qui en reçoit une, un argument ou un résultat de `@task`/`task f(x)` (`_SharesState`). ## Datasets (slice A1.2A)

`dataset Moves of Move { attaquer: {name: 'Attaquer', power: 5}, soin: {…}, }` : une table dont chaque entrée a un nom, qui devient son identifiant typé. Un mold n'embarque plus l'objet, il porte un identifiant de 4 octets : `mold Player { Classes.id job; [Moves.id] coups; }`, `joueur.job.get().atk`. Syntaxe décidée avec l'utilisateur : `of Move` lit les entrées comme un mold **déclaré** (vérifié, bornes comprises ; erreur si inconnu), `as Move` **crée** le mold depuis la première entrée ; les entrées sont écrites (`nom: valeur,`) ou lues d'un fichier JSON (`dataset Moves from "moves.json" of Move;`, ou `as`) ; le type d'un identifiant s'écrit `Moves.id`. L'identifiant est un `IngotSymbol` « Moves.id » (base `uint`, `IngotSymbol.Dataset`) rangé dans `_ingots` sous la clé `Moves::id` : la même clé que le type d'une extension, donc `Moves.id`, `Fichier.Moves.id` et `import Fichier only {Moves}` se résolvent par `_TryFind` sans code en plus. Un identifiant est la **position** de l'entrée ; son nom ne sert qu'à l'écrire et à l'écrire dans les sauvegardes (`id.name()`, `Moves.find(nom): Moves.id?`).

Accroches du binder : `Moves.attaquer` (`_DatasetEntry`, dans `_BindMemberAccess` : `IrRetype` d'un entier sur l'ingot) ; `id.get()` (`_BindDatasetGet` : `IrIndex` **contrôlé** de la table, un identifiant faussé par un calcul arrête le programme) ; `id.name()` (`IrIndex` de la constante des noms `Moves_names`, `[string;N]`, liée comme un precast) ; `Moves.find(nom)` (`IrDatasetFind`, `rgl::standard::dataset_find` dans `runtime/include/rgl/standard/dataset.hpp`) ; toutes dans `_BindCall`. Elles reconnaissent la cible par `_SyntacticType` (étendu : `??`, `?:`, appel de gear, `get()`/`name()`/`find` d'un dataset), car la cible n'est liée qu'une fois ; une cible qu'il ne sait pas typer (un `match`, une lambda…) n'a pas `get()`. Un dataset ne s'importe qu'avec sa table : `_ImportName` importe aussi la constante, `_MemberKey` et `_PublicNames` connaissent `_datasets`. Les entrées ne prennent pas le nom d'un membre (`id`, `length`, `get`, `find`, `name`, E138), sont uniques (E138), un dataset a au moins une entrée (E138).

Fichier de données (`Project/SourceGraph.cs`, `_ExpandDatasets` → `_DatasetEntries`, `JsonConstants.ToDataset`) : le JSON est cherché **par son nom** dans le projet comme pour `import json` (`from "moves.json"` ou `from "moves"`) ; c'est un objet dont les clés sont les noms des entrées, ou un tableau d'objets dont le champ `id` (chaîne) est le nom (retiré du mold) ; chaque entrée est un objet dont les clés sont des noms RGL ; le chargeur écrit un texte RGL `dataset Nom of|as Mold { nom: {champ: valeur, …}, … }` qu'il analyse (positions dans le fichier de données) et dont il ne garde que les entrées. Un **texte** lu du fichier prend le sens du type du champ qui le reçoit (`_dataLiterals`, `_BindDataLiteral`) : variante d'enum (`"element": "Feu"`), identifiant d'une entrée d'un autre dataset (`"job": "mage"`, aussi dans un tableau `"coups": ["attaquer", "braise"]`), sinon un texte ; nom inconnu = E138. Les bornes, les enums et les références exigent donc `of` (le mold créé n'a que des types simples).

Pas encore : table mutable, extension d'un dataset depuis un autre fichier, émission en tableaux `constexpr` triés (la table est aujourd'hui un `soa_array` construit au démarrage : 104 s de compilation Clang pour 5 000 entrées, voir `bench/README.md`), `get()` qui évite de reconstruire l'élément entier (colonne seule), `import` d'un dataset dans un fichier `forge: mold`, XML. Éditeur (extension 0.7.0, `Lsp/SemanticDocument.Datasets.cs`) : un dataset est un symbole `RglSymbolKind.Dataset` (coloré `enum`, plan du document avec ses entrées) ; `DatasetOf` (`Moves`, `bdd.Moves`), `DatasetOfIdType` (`Moves.id`, `bdd.Moves.id`), `DatasetMembers` (entrées = variantes, `id`, `length`, `find`), `DatasetIdMembers` (`get()`, `name()`) ; la complétion après `Moves.`, après un identifiant et après `get().`, dans un nom de type qualifié (`Moves.` dans un champ : `id`), sur l'en-tête `dataset Nom` (`of`/`as`/`from`, puis les molds) ; `TypeOf` donne `Moves.id` à `Moves.nom`, le mold à `get()`, `string` à `name()`, `Moves.id?` à `find` ; définition et survol d'une entrée mènent à sa ligne ; grammaire TextMate (`dataset … of|as`, `mold X -> gear`) et snippets `dataset`, `datasetas`, `datasetfrom`, `moldfin`. **Éditeur de dataset** (extension 0.8.0, `editors/vscode`) : un tableau de webview qui réécrit les entrées du dataset sous le curseur (CodeLens « Éditer le dataset », commande `rgl.editDataset`). Le serveur répond à la requête propre à RGL **`rgl/dataset`** `{textDocument, line}` (`Lsp/DatasetEditorModel.cs`, `LanguageServer._DatasetEditor`) : nom, mold, `createsMold`, fichier `from`, intervalle des accolades à remplacer (`body`), colonnes (champs du mold avec leur type, obligatoire = sans défaut ni nullable, valeurs possibles : variantes d'enum, entrées d'un autre dataset, `true`/`false`, chacune écrite pour le RGL et pour le JSON) et lignes (valeurs écrites par champ, `raw` pour une entrée qu'on ne sait pas découper). L'extension : `dataset-model.js` (**pur**, sans VS Code : `inlineBody`, `jsonText`, `readJson`, `validate`, chargé aussi par la page), `dataset-editor.js` (panneau, CodeLens, `findJson` par nom comme le compilateur, écriture par `WorkspaceEdit` sans enregistrer — le document doit n'avoir pas changé depuis le chargement, sinon « Recharger »), `media/dataset-editor.{js,css}` (la page ; validation en direct, « Appliquer » bloqué tant qu'un nom est invalide, réservé ou en double ou qu'un champ obligatoire est vide). La réécriture du corps ne garde pas les commentaires entre les accolades. Tests : `editors/vscode/test` (`npm test` : le cœur et la page sur un mini-DOM, sans navigateur ni dépendance), `tests/rgl.Tests/Lsp/DatasetEditorModelTests.cs`. Tests de l'éditeur : `tests/rgl.Tests/Binding/DatasetTests.cs`, golden `Golden/parser/dataset`.

## Mode sûr des trains (slice A1.2B, première partie)

`"safe": true` dans `rgl.json` (`ProjectManifest.Safe`, `Binder(…, safe:)`, transmis par `BuildPipeline` et `DocumentAnalysis`) : un train ne cache aucune erreur. Décisions du conseil du 2026-10-26, validées (atelier, slice A1.2B) : le mode sûr ne change ni la syntaxe ni le C++, il refuse des programmes que le mode libre accepte ; `Binder.Safe.cs` (`_CheckSafePath`, appelé après la liaison du train d'entrée et de chaque train appelable, seulement sans autre erreur) parcourt le chemin lié et ses rails. **E139** : un pas (guard appelé, étape d'un parcours `||>` ou `|!|>`, accumulation) dont `GearSymbol.Errors` n'est pas vide et qui n'a pas de rail — y compris un guard appelé dans un rail, qui porte donc son propre rail ; faire échouer le train s'écrit `|> fail` dans un rail, une fin légitime ; l'erreur d'origine traitée par le rail n'entre pas dans `Errors` du train. **E140** : une reprise bornée `^N<M>` (sans `!`) dans un rail, dont l'épuisement continuerait en silence. Un `fail` d'un guard dans une reprise interrompt la boucle (les règles existantes le font déjà). **E141** : le résultat ignoré d'un `spawn` ou d'un `await` écrit comme instruction (W060 et W063 en mode libre ; `task f(x)` jeté est déjà E129). **W065** (`_CheckSafeRail`, `_HandlerIgnoresError`, `_boundGears`) : un rail qui finit en succès (`done`, `$ code`, emit) sans que son premier consommateur — celui qui reçoit l'erreur — lise son paramètre ; il se tait en la lisant, par `|> fail`, ou par la métadonnée `[ignoreError]` sur le handler (`GearSymbol.IgnoresError` ; écrit sans tiret, une clé de métadonnée étant un identifiant). Dans tous les modes (c'était un bug du transpileur), un mold `error` ne contient pas de valeur à cycle de vie (E137, `_CheckErrorMolds`). **Boucles bornées** (clé `loop: "safe"`, `ProjectManifest.BoundedLoops`, `Binder(…, boundedLoops:)`, indépendante de `safe`) : **E142** pour une boucle de guard `g*` ou une reprise `^N` sans limite (`_CheckBoundedLoops`) et pour tout `goto` (`_BindGoto`) ; `g*<N>`, `g*<!N>`, `^N<M>`, `^N<!M>` passent. Limites du certificat et critère d'abandon (les huit bancs du dépôt ne rejettent rien : le seul qui a un guard a déjà ses rails) : voir la note de design. **E143** : un pas du train qui atteint un `@fire` par ses appels (`_CheckNoFire`, par `_calls`). **W066** : un rail qui fait échouer le train avec une autre erreur sans avoir lu celle qu'il reçoit (`_ReceivedErrorRead` sert W065 et W066). Un `fail` seul **après une valeur qui est une erreur** (ou une union d'erreurs : celle qu'un rail reçoit, ou qu'un gear renvoie, `[garder |> fail]`, `[fail]`) envoie cette erreur au lieu d'une `Exception « échec »` (`_BindSteps`, `_IsErrorOrUnion`, `IrPipelineValue` comme erreur) — dans tous les modes. **I002** : le certificat, une information quand le mode sûr accepte le programme : trains et rails vérifiés, liste des rails qui n'ont pas lu leur erreur (`_ReportCertificate`). Note de design : `contexte/Mode sûr - note de design.md`, démo : `contexte/Mode sûr - démo ETL.md`. Tests : `tests/rgl.Tests/Binding/SafeModeTests.cs`.

## Fichiers `forge: native` (slice A2.1a, première tranche)

`forge: native` décrit une bibliothèque C : `header: "lib/x.h"` (un ou plusieurs, chemins relatifs au fichier), `link: static` et `library: {windows: "lib/x.lib", linux: "lib/libx.a"}` (l'archive de la plateforme, facultative). Un fichier `native` ne contient que cet en-tête (E104 sinon) ; `link: dynamic` est **E020** ; ces clés hors d'un fichier `native` sont E104. Décisions du conseil du 2026-10-27 (validées par l'utilisateur : lecture de l'AST par `clang -ast-dump=json`, filtré par fichier, lu en flux) : pas de libclang en P/Invoke (un binaire natif par plateforme contredirait « Zig seul ») ; pas de cache dans cette tranche ; seulement du **C** (`extern "C"`) ; les déclarations non converties sont laissées de côté, avec une notice, jamais une erreur de Clang.

Réalisation : `import Mathx;` charge `Mathx.forge` comme n'importe quel fichier ; `SourceGraph.Loader._ExpandNative` le **remplace** par un fichier `forge: gears` engendré : `ICompilerToolchain.DumpHeaderAst` lance `zig clang -x c -target T -Xclang -ast-dump=json -fsyntax-only` (pas `zig c++`, qui prépare un objet dans son cache et échoue à le renommer ; son code de sortie est 0 pour un en-tête sain, 1 pour une erreur), `Native/ClangAstReader` lit le JSON au fil de l'eau (`Utf8JsonReader`, tampon de 1 Mo, 41 Mo de mémoire pour 297 Mo de JSON sur `windows.h`, 1,6 s) et ne garde que les déclarations dont `loc.file` est l'en-tête demandé — Clang n'écrit `file` que lorsqu'il change, donc le fichier courant se suit sur tout le flux, et un `file` sous `includedFrom` est celui de l'inclueur, à ignorer ; les `typedef` sont retenus où qu'ils soient (`size_t` est dans un en-tête du système) et résolus par la table de conversion. `Native/CBindings` écrit une fonction par gear : `gear add(int a, int b): int { return native add(a, b); }` ; `native f(x)` (`AST/Expressions/NativeCallExpression`, lu seulement quand `Parser.AllowNativeCalls`) est lié par `Binder.Native.cs` en `IrNativeCall` (type = retour du gear enveloppant) et émis `::f(x)` ; le reste du programme appelle ces gears (non purs) comme les autres. Table de conversion, dépendante de la cible (`ICompilerToolchain.Target` : `long` a 32 bits sous Windows, 64 ailleurs) : entiers, `bool`, `float`, `double` ; pointeurs, structs, énumérations, variadiques, `char`, noms réservés de RGL : laissés de côté avec leur raison (`CBindings.Result.Unconverted`) et résumés dans une notice. `SourceModule.Native` (`Native/CLibrary` : en-têtes, dossiers, archive) passe par `IrProgram.Natives` et `CppProgram.Natives` : le C++ généré inclut chaque en-tête dans `extern "C" { … }` et `ZigToolchain` ajoute les `-I` et l'archive à l'édition de liens. Un en-tête que Clang refuse, ou une chaîne de compilation absente, est **E144** : c'est un diagnostic du fichier de l'utilisateur (avec les premières lignes de Clang), pas un « bug du transpileur » — c'est la seule exception à la règle « aucune erreur Clang ne doit atteindre l'utilisateur », et seulement pour la lecture d'un en-tête, jamais pour le C++ généré. Tests : `tests/rgl.Tests/NativeTests.cs` (lecteur sur du JSON figé, table de conversion, bout en bout avec une bibliothèque C compilée en `.a` par Zig). Pas encore : cache des liaisons (clé : contenu des en-têtes, version de Clang, options, **cible**), structs/enum/`const char*`/`ptr<T>` (`unsafe` n'existe pas), macros `#define` (invisibles dans l'AST), `rgl check`/E019, `NativeError`, LSP (un fichier `native` est une erreur E144 dans l'éditeur tant que `DocumentAnalysis` n'a pas de chaîne de compilation), `import native`.

**Slice A2.1b** : les `struct`, les `enum` et `const char*` passent la frontière. Un `struct` complet (`RecordDecl` avec `completeDefinition`) dont tous les champs sont convertibles devient un `mold` du même nom ; un `typedef` donne son nom à un struct ou une enum anonyme (le `TypedefDecl` porte `inner[0].decl.id`, l'identifiant du `RecordDecl` sans nom : `ClangAstReader.Declarations`) ; une enum devient `enum Nom: int { A: 0, B: 4 }` avec les valeurs du C (celle de la précédente plus un quand elle n'est pas écrite) ; `const char *` est une `string`, copiée dans les deux sens, mais pas dans un champ de struct (le texte n'a pas de propriétaire connu) ; `char *` (modifiable), unions, champs de bits, struct incomplets, enums sans nom, noms réservés de RGL, deux constantes de même valeur : laissés de côté avec leur raison. `CBindings.Generate` écrit dans l'ordre enums, molds, gears (un struct ne contient que des types déjà définis). Émetteur (`CppEmitter.Native.cs`) : rien n'est supposé de la disposition du struct C ni du nom de ses types, que le C++ généré n'écrit jamais — un mold passé à une fonction est une **liste d'initialisation** de ses champs (`::echelle({v.rgl_f_x, v.rgl_f_y}, k)`, le paramètre C en déduit son type), une enum un proxy `rgl::standard::native::enum_value` (`runtime/include/rgl/standard/native.hpp`, se convertit en n'importe quelle enum) ; au retour un struct est reconstruit champ par champ (lambda appelée sur place), une enum par `static_cast`, un texte par le constructeur de `string` (qui copie, et donne la chaîne vide pour une adresse nulle). Les types viennent de la table : `Context.Structs`/`Enums`, alias résolus (`struct Vec2`, `enum Color`). Pas encore : macros `#define` (invisibles dans l'AST ; il faudra `-E -dD` et ses repères de fichier), union, tableau dans un struct, pointeurs, `unsafe`. Démo : `demo/native` (`build.ps1`).

**Macros (fin de A2.1b)** : l'arbre de Clang ne voit pas les `#define`. `ICompilerToolchain.DumpHeaderMacros` lance un second `zig clang -x c -target T -E -dD` (le source préprocessé garde ses `#define` et ses `#undef` entre des repères `# 12 "fichier" 1` qui disent de quel fichier vient la suite) et `Native/CMacroReader` n'en garde que ceux du fichier demandé. Seules les macros sans paramètres qui valent un **littéral** deviennent des constantes (`const int VERSION_MAJOR: 3;`, écrites avant les gears, comme tout fichier de gears) : entier (décimal, hexadécimal, octal, binaire, suffixes `U`/`L`, signe, parenthèses ; `int`, sinon `uint` pour un `U` ou un hexadécimal qui y tient, `long`, `ulong`), flottant (`double`, point toujours écrit : `1e3` devient `1.0e3`, le suffixe `f` est ignoré) ou texte (`\\`, `\"`, `\n`, `\r`, `\t` seulement). Une macro redéfinie vaut sa dernière définition, une macro retirée (`#undef`) disparaît. Laissées de côté, sans notice : macros à paramètres, expressions (`(A * 2)`), renvois à une autre macro, types, valeur vide (les gardes d'inclusion), et une macro dont le nom est celui d'une fonction, d'un struct ou d'une enum de l'en-tête. Un échec du préprocesseur est E144 comme celui de la lecture de l'arbre. Le coût : un second passage de Clang par en-tête (pas de cache encore).

**Cache des liaisons (A2.1c)** : `Native/NativeCache` range le texte RGL engendré d'un fichier `forge: native` dans `<cache>/native/<clé>.rgl` (première ligne `// notice`, puis les liaisons ; `SourceGraph.Load(…, nativeCache:)` reçoit le dossier de `BuildPipeline`, pas le LSP, qui n'a pas encore de chaîne de compilation). La clé est le SHA-256 du nom de la chaîne (sa version fixe celle de Clang), de la cible, de l'identifiant du module du compilateur (une nouvelle version peut écrire d'autres liaisons), du nom du fichier et du **contenu de chaque en-tête et de tout ce qu'il inclut** : la liste vient de `ICompilerToolchain.ListHeaderDependencies` (`zig clang -x c -MM`, 60 ms, hors en-têtes du système, que la version de Clang représente), lue comme une règle de Makefile (`NativeCache.Parse` : lignes jointes par `\`, `\ ` dans un nom). Un cache qui sert évite le passage de l'arbre et celui du préprocesseur ; il ne sert qu'à aller plus vite : manquant, illisible (« n'importe quoi » est ignoré) ou impossible à écrire, les liaisons sont refaites, et si `-MM` échoue la clé est `null` et la lecture normale signale l'erreur (E144). Le fichier est écrit sous un nom temporaire puis renommé. Tests : `NativeTests` (cache servi, en-tête modifié, en-tête inclus modifié, cache abîmé, `Parse`) avec une chaîne qui compte les lectures d'arbre. Pas encore : nettoyage des vieilles entrées du cache, cache dans le LSP.

## `rgl check` et `rgl cache`

**`rgl check [fichier.rgl | -d dossier] [--all] [--strict]`** (`Cli/CheckCommand.cs`) : le bilan de l'intégration C++. Sans fichier ni dossier, le projet du dossier courant. Charge le projet comme un build (`SourceGraph.Load` avec la chaîne de compilation et le cache des liaisons ; les notices de lecture sont tues, le bilan les remplace), écrit une ligne par fichier `forge: native` (`CLibrary.Summary` : fonctions, types et constantes convertis, déclarations non prises en charge) puis cherche dans le code du projet — fichiers autres que les natifs et la std, qui importent le fichier natif — les symboles non convertis qu'il nomme : `Module.nom` (nom local de l'import, alias compris) ou `nom` seul quand `only { nom }` le rend visible, jetons lus par le lexer (ni commentaires ni chaînes). Chaque emploi est **E019** à sa place (avec la raison, `CLibrary.Unconverted`) ; sans emploi, le symbole n'est listé qu'avec `--all` (notice). Par défaut la commande réussit même avec des E019 (c'est un rapport) ; `--strict` renvoie 1 s'il en reste. Les raisons viennent de `CBindings.Result.Unconverted`, gardées dans le cache (`NativeCache.Entry`, lignes `//~ nom<TAB>raison` après la première ligne `// <déclarations non lues><TAB><bilan>`). `rgl compile` ne fait pas ce rapport : un appel non converti y reste « gear introuvable » (E035).

**`rgl cache --size`** écrit « Cache : 280,6 Mo (chemin) » (`CacheCommand.Format` : o, Ko, Mo, Go, 1024, une décimale, virgule française) ; **`rgl cache clear`** supprime tout le contenu de la racine du cache (C++ généré, objets du runtime, caches de Zig, liaisons : tout se refait au build suivant, le runtime en une vingtaine de secondes) et garde son dossier ; il refuse une racine de disque ou le dossier personnel (jamais vidés par erreur), continue après un fichier qu'il ne peut pas supprimer et échoue alors. **W067** : le cache prend 2 % du disque ou plus (`CacheCommand.WarningShare`, `Warn`) — signalé par `cache --size` et après chaque `compile`/`exec`, même en échec (un parcours du cache à chaque build). `CliContext.DiskSize` remplace la taille du disque lue par le système, pour les tests. Tests : `tests/rgl.Tests/CheckAndCacheTests.cs` (une chaîne de compilation figée, sans Zig).

## `NativeError` et le composant `Native` (slice A2.3, début)

Décision de l'atelier (conseil du 2026-10-27, cinq avis, un prototype) : **`NativeError` = `message` + `where` + `callee`** (`std/Errors.forge`, `error NativeError { string callee; }`, sans `...StandardError`, donc sans `code`). `message` : le `what()` de l'exception, sinon « exception C++ inconnue » (`throw 42`, `catch(...)`) ; `where` : la position RGL de l'appel, pas celle du `throw` ; `callee` : la fonction ou méthode C++ telle qu'écrite dans la liaison, sans mangling (le nom `symbol`, d'abord choisi, est impossible : c'est un nom de type de RGL, E011). Pas de type C++ d'origine (RTTI désactivé, non déterministe d'un compilateur à l'autre), pas de `code` ni de `kind` (un champ presque toujours faux est pire qu'absent ; un champ s'ajoute sans rien casser par duck typing, un champ retiré casse tout). Seules les liaisons de niveau 2 et 3 (C++) ajouteront `NativeError` aux erreurs d'un guard ; les gears importés d'un en-tête C (A2.1) n'en ajoutent pas ; un natif qui renvoie un code d'erreur n'est pas une exception.

Le `try/catch` ne vit **jamais** dans le C++ généré (`-fno-exceptions`) : `RuntimeComponent.Native` (`runtime/src/native.cpp`, `runtime/include/rgl/standard/native.hpp`) est le **seul fichier du runtime compilé avec les exceptions** (`ZigToolchain._WithExceptions` : `-fexceptions` à la place de `-fno-exceptions`, RTTI toujours désactivé — vérifié, un `catch` par type n'en a pas besoin), lié seulement si le programme l'utilise (coût nul sinon ; environ +158 Ko avec la machinerie d'exceptions de libc++). `int rgl_native_guard(void (*body)(void*), void* context, rgl_native_status* status) noexcept` appelle `body` et rend 0, ou 1 avec `status->message` (256 octets, tronqué, toujours terminé par zéro) pour une `std::exception` ou autre chose. **Règle** : `body` est du code compilé avec les exceptions ; une exception qui traverserait du code compilé sans exceptions arrête le programme (`terminate called after throwing…`, vérifié) — le C++ d'une liaison et ce qui l'appelle sont donc dans une unité à exceptions, jamais dans le C++ généré. Un code qui a une archive compilée avec les sanitizers de Zig ne se lie pas en release (symboles `__ubsan_*`) : compiler l'archive avec `-fno-sanitize=undefined`. Tests : `tests/rgl.Tests/NativeExceptionTests.cs` (une archive C++ qui lance `runtime_error`, `throw 42`, `bad_alloc`, une exception imbriquée et un message de 1000 caractères, appelée à travers le vrai `ZigToolchain.BuildExecutable` en debug et release ; `std.NativeError` utilisable par un guard). Pas encore : `.rgl.cpp`, `descriptor`, `wrapper`, le squelette de descriptor, l'émission d'un appel protégé et l'ajout de `NativeError` aux erreurs d'un guard natif (le binder ne prend pas encore le mold par identité).

## Composants écrits en C++ : `.rgl.cpp` (slice A2.3, niveau 2)

`guard normalise(string texte): string;` — un guard **sans corps** (`GearDeclaration.IsNative` : ni bloc ni `=>`) — est implémenté par `normalise.rgl.cpp`, écrit **à côté du fichier forge** qui le déclare, au nom exact du gear (un gear par fichier). Décisions de l'utilisateur (plan du 2026-10-27) : un seul composant par `.rgl.cpp` ; il est obligatoirement un `guard` (le C++ peut lancer) ; types permis : entiers, flottants, `bool`, `string` (et `void` en retour), les molds, tableaux, enums viendront ensuite ; le C++ à la main voit les types du runtime. Parser : `;` après le type de retour. `FileChecks._CheckNativeComponents` : seulement dans un `forge: gears` (E104 ailleurs, `.rgl` d'entrée compris), **E145** pour un `gear`/`emit`, un générique, un paramètre `mut`/`params`/`this`/à valeur par défaut. `SourceGraph.Loader._FindNativeSources` cherche `nom.rgl.cpp` dans le dossier du fichier forge (E145 s'il manque) et le range dans `SourceModule.NativeSources` ; `Binder.NativeComponents.cs` (`_BindNativeGear`) vérifie les types (E145), refuse deux composants de même nom (la fonction C++ s'appelle `rgl_native::nom` dans son unité : deux définitions ne se lieraient pas), donne au guard la seule erreur `std.NativeError` (`_nativeError`, pris dans `std.Errors` ; sans la std : « pas encore pris en charge ») et met `GearSymbol.NativeSource`.

C++ généré (`CppEmitter.NativeComponents.cs`) : le programme, compilé sans exceptions, n'appelle jamais le C++ du composant directement. Le guard `rgl_g_X(args…, const char* rgl_where)` — `rgl_where` est la **position RGL de l'appel**, ajoutée par `_CallText` à chaque appel d'un composant — range ses arguments dans un contexte (`struct rgl_nat_X_ctx { P0 a0; … R result{}; }`, défini dans le programme et dans l'unité), appelle `rgl_native_guard(&rgl_nat_X_thunk, &ctx, &status)` (composant `Native`, voir plus haut) et, en cas d'exception, échoue avec `NativeError{message, where = rgl_where, callee = "nom"}`. L'**unité** (`CppProgram.NativeUnits`, `NativeUnit`, écrite en `<cache>/projets/<p>/cpp/<CppName>.rgl.gen.cpp`) contient le contexte, la déclaration `namespace rgl_native { R nom(params); }`, le fichier de l'utilisateur inclus **tel quel** (`#line 1 "chemin"` : les erreurs de Clang pointent vers lui) et `extern "C" void rgl_nat_X_thunk(void*)`. Le fichier de l'utilisateur définit donc `rgl_native::nom(…)` avec les types du runtime (`rgl::standard::string`, `std::int32_t`, `double`…) sans rien inclure pour eux ; il inclut lui-même ce que son code utilise (`<string>`, `<stdexcept>`).

Compilation : `BuildPipeline` compile chaque unité **avant** le programme par `ICompilerToolchain.CompileNativeUnit` (`-fexceptions`, RTTI permis : c'est du code écrit à la main), puis lie les objets au programme (`CLibrary` dont la bibliothèque est l'objet). Un échec est **E146**, une erreur du fichier de l'utilisateur avec les huit premières lignes de Clang — jamais « bug du transpileur ». Un `--emit-cpp` écrit les unités sans les compiler. Tests : `tests/rgl.Tests/NativeComponentTests.cs` (valeur rendue, `std::invalid_argument` → rail, `throw 42` → « exception C++ inconnue », entiers et propagation d'un guard à l'autre, guard `void` et flottant, erreur de C++ = E146, déclarations invalides = E145). Pas encore : `descriptor`, `wrapper` et le squelette de descriptor (niveau 3), molds/tableaux/enums à la frontière, trains en C++ (la spec dit « gear ou train »), un cache des objets d'unité (recompilés à chaque build), un projet de plusieurs composants de même nom dans des dossiers différents, l'éditeur (le LSP ne voit pas ces fichiers).

## Descriptors : une classe C++ vue de RGL (slice A2.3, niveau 3a)

`forge: descriptor` (`header:`, `link:`, `library:` comme `forge: native`, puis des descriptors) : `descriptor demo::Counter -> Compteur { constructor(int start) => demo::Counter(start); add(int n): int => add; const field total: int => $self.total(); static Zero(): Compteur => Zero; }`. Décisions de l'utilisateur (plan du 2026-10-27) : (1) la valeur RGL est un type **opaque et déplaçable**, jamais copiable, dont le destructeur C++ s'appelle tout seul ; (2) à gauche de la flèche d'un membre la signature RGL, à droite le C++ ; (3) chaque constructeur, méthode ou statique est un **guard** (`NativeError`, voir plus haut) ; (4) nombres, `bool` et `string` sont copiés à la frontière, un type décrit passe par son adresse, pas de référence ni de pointeur renvoyés ; (5) un fichier `.forge` d'un genre à part ; (6) deux niveaux de wrappers seulement (pas encore faits). Pas encore : les descriptors génériques (`descriptor X<T> -> ChainedList<T>`), `wrapper`, le squelette généré depuis un en-tête (3b, 3c), l'écriture d'un champ, les surcharges, l'héritage, les molds/tableaux/enums à la frontière.

Parser : `AST/Descriptors` (`DescriptorDeclaration` : type C++ gardé comme texte, `DescriptorMember` : `Constructor`, `Method`, `Static`, `Field` + `const`, l'expression C++ gardée telle qu'écrite jusqu'au `;` de même niveau), `Parser.Descriptors.cs` (`descriptor` est un mot-clé ; `constructor`, `field`, `static` sont contextuels). `FileChecks` : genre `descriptor`, E104 pour un descriptor hors de ce genre (`.rgl` d'entrée compris) et pour autre chose qu'un descriptor dedans, E145 pour un membre en double ou avec `mut`/`params`/`this`/valeur par défaut. **Chargeur** : `SourceGraph.Loader._ExpandDescriptors` remplace le fichier par un texte RGL engendré (`Native/DescriptorBindings`) — comme `forge: native`, sans Clang : le C++ n'est jamais lu, l'unité l'inclut — : un `mold Compteur -> Compteur__fermer { ulong handle; }` (l'adresse de l'objet C++ ; le cycle de vie de A1.1 donne gratuitement move-only, E136 pour une copie et la destruction unique chez le nouveau propriétaire), un `gear Compteur__fermer(Compteur c): void;` sans corps (pas un guard : un destructeur ne peut pas échouer, une exception y est ignorée) et un `extend Compteur { guard create(…): Compteur; guard add(this Compteur _self, int n): int; … }` — le constructeur est la statique `Compteur.create` (`new` est un mot-clé), un champ se lit comme une méthode (`c.total()`, pas de syntaxe de propriété). Le C++ de chaque guard sans corps n'est pas dans le texte : le chargeur le garde dans `SourceModule.NativeBodies`, par position du nom du gear dans le texte (`NativeBody` : `Expression`/`Destroy`, `SelfIndex`, `Classes` — le type C++ de chaque type décrit —, `Headers`). Une expression qui n'est qu'un nom est développée : méthode `$self.nom(args)`, statique `Type::nom(args)`, champ `$self.nom`, constructeur `nom(args)`.

Binder : `GearSymbol.NativeBody` (`IsNative`, `IsNativeGuard`), `_BindNativeGear` accepte maintenant `NativeSource` ou `NativeBody` et les types décrits (`_IsNativeType`). Une extension nommée `add`, `push` ou `has` s'applique à un type qui n'est pas une collection (`_BindCall` essaie l'extension avant la méthode de collection quand le type syntaxique de la cible n'est ni tableau ni dictionnaire). Émetteur (`CppEmitter.NativeComponents.cs`) : même schéma que `.rgl.cpp` (contexte, `rgl_native_guard`, unité compilée avec exceptions) ; un type décrit est `std::uint64_t` dans le contexte (`c.rgl_f_handle` à l'aller, `rgl_m_Compteur{ctx.result}` au retour) ; dans l'unité `$self` est `(*reinterpret_cast<Classe*>(a0))`, `$argN` le N-ième argument (après `$self`) — un paramètre peut aussi s'écrire par son nom RGL (sauf après `.`, `::`, `->`, ou avant `(`) —, un résultat de type décrit est `reinterpret_cast<std::uint64_t>(new Classe(expression))` (copie élidée : la classe n'a pas besoin d'être copiable, seulement déplaçable), la destruction `delete reinterpret_cast<Classe*>(a0)`. Une `string` C++ se convertit dans l'expression (`rgl::standard::string(x.c_str())`, `std::string(a.data(), a.size())`). `NativeUnit` porte maintenant `IncludeDirectories` (ceux des en-têtes). Le `callee` d'une `NativeError` d'un membre est `Compteur.add` (le nom du gear d'extension). Tests : `tests/rgl.Tests/NativeDescriptorTests.cs` (création, lecture, méthode, exception au rail, texte, statique qui renvoie un objet, destructeur appelé une fois, copie refusée, fichiers invalides), golden `Golden/parser/descriptor`. Démo : `demo/native-cpp`.

## Squelette de descriptor : `rgl descriptor` (slice A2.3, niveau 3c)

`rgl descriptor <en-tête> --class ns::Classe [--name Nom] [-o fichier] [-I dossier]…` (`Cli/DescriptorCommand.cs`) lit l'en-tête **C++** avec Clang et écrit le squelette d'un fichier `forge: descriptor` de la classe, sur la sortie standard ou dans un fichier qu'il **n'écrase jamais** (le chemin de `header:` est relatif au fichier écrit). Le wrapper (3b) est abandonné pour l'instant (décision de l'utilisateur : on y reviendra s'il y a un vrai besoin).

Lecture : `ICompilerToolchain.DumpHeaderAst(…, cpp: true)` (`zig c++ -x c++ -std=c++23 -Xclang -ast-dump=json -fsyntax-only`) ; `ClangAstReader` (la même lecture en flux filtrée par fichier que pour le C) range maintenant dans `CHeader.Classes`/`ClassTemplates` ce que `Native/CppReader` lit des `NamespaceDecl`, `CXXRecordDecl` (définition complète seulement) et `ClassTemplateDecl` : les membres **publics** (suivi des `AccessSpecDecl`, `class` privé par défaut, `struct` public), constructeurs (copie, déplacement, supprimés et implicites écartés), méthodes (statique par `storageClass`, `const` et `virtual`), champs, la classe abstraite (`definitionData.isAbstract`), les bases (jamais reprises), et `skippedMembers` pour les opérateurs et les patrons de fonction. Le type de retour d'une méthode se sépare des paramètres par `CppReader._SplitSignature` (la dernière parenthèse fermée avant `const`, `noexcept`, `&`). `Native/DescriptorSkeleton` écrit un membre par ce que RGL sait décrire : entiers, flottants et `bool` (`CBindings.Scalar`, la table de A2.1, dépendante de la cible), `std::string` (`std::string($argN.data(), $argN.size())` à l'aller, `rgl::standard::string((x).c_str())` au retour, champs compris), la classe elle-même par `const&` en paramètre et par valeur en retour ; **tout le reste est écrit en commentaire avec sa raison** : pointeur, référence rvalue, référence non constante en paramètre, **toute** référence renvoyée (décision 4 du plan), objet passé par valeur, type inconnu, mot réservé de RGL, opérateur, surcharge (la première est gardée : un nom par membre), patron de fonction. Une expression sans conversion est le nom seul (`add => add`, développé par le chargeur), sinon l'expression complète. Erreurs : en-tête absent, chaîne de compilation absente ou en-tête que Clang refuse (E144), classe inconnue (liste les classes définies) ou patron de classe (« pas encore pris en charge »).

**Deux corrections au passage.** (1) `DumpHeaderAst`, `DumpHeaderMacros` et `ListHeaderDependencies` appellent maintenant `zig cc`/`zig c++` et non plus `zig clang` : ce dernier est le pilote Clang nu, qui **trouvait les en-têtes C d'un MinGW installé sur la machine** (`C:/Users/…/mingw64`) au lieu de ceux de Zig — A2.1 ne marchait donc pas sur une machine sans lui, et en C++ il échouait (`mm_malloc.h`). `zig cc -fsyntax-only` prépare tout de même un objet dans son cache et échoue parfois à le renommer : ce seul « failed to rename » n'est pas un échec (`_DumpHeader(…, syntaxOnly: true)`). (2) La lecture JSON refusait les arbres de plus de 64 niveaux (patrons de la bibliothèque standard) : `MaxDepth` est maintenant de 4096. Tests : `tests/rgl.Tests/DescriptorSkeletonTests.cs` (un AST figé avec tous les cas limites, classe abstraite, fichier jamais écrasé, classe inconnue, usage, séparation de la signature, et la boucle complète avec Zig : la commande écrit le squelette d'une vraie classe, un programme s'en sert tel quel et affiche `compteur=15`). Pas encore : les descriptors génériques (patrons de classe), l'écriture d'un champ, les surcharges, l'héritage, un squelette qui fusionne avec un fichier déjà retouché, `wrapper`.

## Complément A2.3 : frontière C++ complète

Les descriptors acceptent maintenant leurs paramètres génériques de type, les surcharges de constructeurs/méthodes/statiques et les champs modifiables (`set_nom(valeur)`, lecture `nom()`, pas de setter pour `const field`). `DescriptorBindings` conserve les noms publics dans `NativeBody.PublicName` ; le binder spécialise les expressions C++, les extensions et le destructeur opaque pour chaque instanciation. Un appel ambigu est E145. `GenericTypeExpression` représente `Cpp.Boite<int>` avant un accès statique. Le générateur de squelette conserve les surcharges représentables ; pour un champ à conversion, il écrit une paire explicite de méthodes afin que le setter ne tente pas d’assigner un temporaire.

La frontière accepte aussi enums/ingots/molds sans cycle de vie et tableaux ; l’émetteur fournit leurs déclarations C++ aux unités natives. Les tableaux de molds qui traversent cette frontière restent AoS, indépendamment des champs chauds des parcours. Les objets décrits restent des poignées move-only, y compris les instances génériques. Les dictionnaires et collections d’objets à cycle de vie ne sont pas acceptés.

Un train natif écrit `train(params): T;` dans `forge: train` : implémentation `NomDuFichier.rgl.cpp`, fonction `rgl_native::NomDuFichier`. Dans un bloc nommé `train nom { train(params): T; }`, utiliser `nom.rgl.cpp` et `rgl_native::nom`. Résultat explicite, exceptions sur NativeError ; pas de `!train` ni options de paramètres natives. Le train par défaut reste obligatoire.

`ZigToolchain.CompileNativeUnit` cache les objets sous `native-units` en couvrant les inclusions transitives (`-MM` avec les options de compilation), leur contenu, le profil, la cible, Zig et le compilateur RGL. L’éditeur expose les descriptors depuis leurs AST originaux (signatures, complétion, navigation), sans décaler les positions vers un texte engendré. Voir `Docs/NativeInterop.md` et les tests `NativeComponentTests`, `NativeDescriptorTests`, `DescriptorSkeletonTests`, `Lsp/DescriptorEditorTests`. Le wrapper reste différé ; l’atelier n’est pas modifié automatiquement.

## A2.4 — unsafe, pointeurs et pack

Les blueprints sont différés **après la v1**, selon le besoin (instruction utilisateur du 2026-10-27) ; ne pas les implémenter dans cette slice.

Contrat utilisateur : `ptr<T> p: valeur;` alloue directement, sans nouveau `new` RGL. `ptr<T>` possède son objet, le libère à sa destruction et ne se copie jamais (cycle de vie A1.1, E136). `uptr<T>` n’a pas de libération automatique. `p.free`/`p.free()`, `delete p` et `undefine p` libèrent l’objet et invalident le nom ; `::` et `<-|` transfèrent entre ptr et uptr dans les deux sens. W068 signale une libération possiblement manquante d’un uptr local, avec analyse des branches et sorties. Une adresse `&x` est un uptr emprunté, pas une allocation à adopter ou libérer.

Réalisation : AST/IR `PointerType(Owned)`, `IrRawMemory`, runtime `pointer<T, Owned>`, `Binder.Unsafe.cs`, `Binder.PointerLeaks.cs`. `unsafe f(...)` est un gear sans done/fail. E147 hors contexte unsafe pour les types et opérations brutes ; propagation dans le graphe d’appels et les trains, refus par le mode safe. `char` = char C++ 8 bits, conversion explicite entière. L’unité native reçoit/rend T* ; le wrapper RGL garde la propriété. Les exceptions d’un composant déclaré unsafe arrêtent le programme ; les guards natifs conservent NativeError et leurs rails.

`pack(tableau)` est un intrinsèque : `IrArrayPack`, `ArrayType.Packed`, copie AoS récursive via `array_pack.hpp`. Les signatures natives portent leur représentation sans désactiver SoA globalement pour tous les tableaux du même mold (remplace le choix provisoire A2.3). E148 si pack est nécessaire. Tests : UnsafeTests, NativeComponentTests, golden unsafe-pointers ; documentation Docs/Unsafe.md. Les compositions de propriétaires suivent les limites A1.1 ; la suppression dynamique de colonnes reste absente.

Extension 0.9.0 : snippets natifs et mémoire, en-têtes `descriptor`/`precast`/`extend`, coloration des déclarations `unsafe`, survol des opérations brutes. Les membres de descriptors génériques conservent leur AST original tout en substituant les types des paramètres et retours pour les signatures et la déduction locale.

`Lsp/NativeEditorModel.cs` fournit au chargeur la chaîne Zig et le cache natif utilisé par la compilation. Garder cette information quand le lancement du serveur évolue.


## A2.4B — C++ intégré et confiance

`cpp { ... }(Type nom: valeur): Retour` est une expression à corps C++ opaque
(`CppBlockReader`, AST `CppExpression`). Elle crée un gear natif interne ; les arguments
s’évaluent une fois de gauche à droite. Les alias C++ `rgl_arg_NOM` et `rgl_return`
évitent de dupliquer la représentation des types. La signature exacte de l’entrée
C++ `rgl` est contrôlée, `noexcept` permis. Les blocs sont isolés par namespace ;
les includes restent globaux, y compris sous conditions du préprocesseur.

`@trusted` (`@trust` alias) autorise une interface sûre autour d’unsafe/cpp.
`pure` reste orthogonal (`unsafe pure` permis) : le RGL est vérifié ; les blocs
natifs d’un gear pure trusted sont attestés par l’auteur. La traversée safe arrête
la propagation unsafe à cette frontière mais continue de refuser @fire.
Une exception C++ du bloc arrête le programme comme en A2.4, pas de NativeError implicite.
`std.sqrt` utilise désormais cette frontière pure trusted.

Les types fonction compatibles peuvent franchir cette frontière comme callbacks synchrones ;
le C++ les reçoit via `rgl_arg_NOM` et ne doit pas conserver leur référence sans garantir sa
durée de vie. `std/Http.forge` s'appuie sur ce mécanisme pour garder le routage en RGL tandis
que `runtime/src/http.cpp` fournit le serveur/client HTTP/1.1 (IPv4 et IPv6, connexions persistantes), un pool de workers et
WebSocket texte. `runtime/src/http_tls.cpp` ajoute HTTPS et WSS via OpenSSL, dans le composant
`HttpTls` lié seulement à la demande (`RGL_OPENSSL_INCLUDE`/`RGL_OPENSSL_LIB` hors des chemins
Linux habituels). Les certificats clients sont vérifiés. Les requêtes restent bloquantes par
worker, acceptent `Content-Length` jusqu'à 1 Mio et ferment chaque connexion ; voir
`Docs/Http.md` pour l'API, les limites et les variables d'environnement.
`HttpServer.webSocketCircuit` reçoit une fabrique appelée après le handshake : elle rend une closure
persistante propre à la connexion, utilisée pour ses frames puis détruite à sa fermeture. `webSocket`
reste le raccourci sans état de connexion. `staticFiles()` ajoute le dossier `static` de l'exécutable
comme fallback GET protégé contre les remontées de chemin.

### Surcharges de gears

Les gears ordinaires, génériques et d'extension peuvent partager un nom si leurs paramètres diffèrent. `Binder.Gears` conserve les groupes dans `_gearOverloads` et choisit par nombre d'arguments, nombre de conversions implicites, défauts utilisés puis `params`; une signature non générique gagne à rang égal, une instance générique exacte gagne contre une conversion. Le retour, les noms, les effets, `mut` seul et la sorte gear/guard/emit ne distinguent pas une signature (E055). Deux meilleures candidates donnent E152. Les groupes suivent les imports qualifiés et `only`; une référence de fonction surchargée utilise son `FunctionType` attendu. Le LSP conserve les déclarations dans `ModuleInfo.Overloads` et publie toutes les aides de signature. Voir `Docs/GearOverloads.md` et `GearOverloadTests`.

Manifeste : `no-trust`, `no-cpp` (false par défaut), `cpp-trust` (tableau de chemins
relatifs de fichiers forge explicitement autorisés). La std authentique est exemptée.
Une autorisation ne s’étend pas aux imports. Les chemins physiques empêchent une
liste de confiance de sortir de la racine par lien symbolique. `NativePolicy`
est commun à SourceGraph, Binder, BuildPipeline et au LSP. Le code C++ arbitraire
n’est pas sandboxé. E149 : bloc/inclusion invalide ; E150 : politique native ;
E151 : annotation trusted invalide. Voir Docs/InlineCpp.md. Extension VS Code 0.10.0.

## Pipeline lambda et import de fichier

`v |> (x) => expression` fonctionne dans une expression et comme étape d’un train. La lambda reçoit exactement un paramètre, lié au type de la valeur courante, puis devient un `IrInvoke`; elle a donc le comportement d’un gear et ne peut porter ni rail de guard ni terminaison d’emit. AST : `LambdaPipeExpression` et `LambdaStep`; l’émetteur de train accepte un `IrInvoke` dans `IrStep.Value`.

`import file "nom.ext" as constante;` lit le premier fichier UTF-8 portant exactement ce nom, selon l’ordre ordinal du parcours, et engendre une constante `string`. `FileScope.RawFiles` garde tous les fichiers de la portée ; les boxes restent opaques et `import [..] file "nom.ext" as constante;` sélectionne la portée du projet. Le contenu passe par un littéral RGL échappé afin de réutiliser le lexer, le binder et la génération habituelle des constantes.

Les `assets` de `rgl.json` sont des chemins ou globs relatifs (`front/html/**`). `ProjectAssets.Resolve` les vérifie avant compilation, ignore `out` et les liens de dossiers, puis `Copy` conserve leur chemin sous `out/<profil>` après l'édition de liens. Un motif vide est une erreur. `std/Path.forge` expose `currentDirectory`, `executablePath`, `executableDirectory` et `findFile`. La frontière C++ de `string` expose `from_cstr`, `from_std_string`, `to_std_string`, `view` et un constructeur depuis `std::string`.

## Paper

Les `.paper` sont indexés par `SourceGraph` dans la même portée de fichiers que les `.forge` et sont compilés par `PaperCompiler` en module `forge: gears`. Tous les blocs `@rgl` partagent ce module. `std/Paper.forge` exporte l'ingot `html`, `DomEvent` et `escapeHtml`; une interpolation ordinaire devient un fragment échappé, `html(...)` un fragment brut. `import [..] file` est reconnu directement par Paper et n'entre pas dans la grammaire d'expression RGL.

`reactive TYPE nom: valeur;` devient un champ du mold exporté `State`. Les fragments reçoivent l'état et déclarent leurs dépendances. Les attributs `@click`/`@input`/`@change`/`@submit`/`@keydown`/`@keyup` désignent un gear sans paramètre ou avec `DomEvent`; `dispatch` exécute le handler et renvoie les ids des fragments qui lisent l'état écrit. Le HTML initial encadre chaque interpolation par `<!--rgl:fN-->`/`<!--rgl:/fN-->`. Le guard généré `mount(HttpServer, path): HttpServer` transforme le serveur dans un pipeline, configure HTTP, le runtime et `webSocketCircuit`; chaque connexion obtient sa propre closure contenant un nouveau `State`. `std/Web.forge` fournit `Web.createServer`, `Web.staticFiles`, `Web.staticFilesFrom`, `Web.listen`, `Web.listenOn` et `Web.listenWith` pour construire le serveur sans variable `mut`.

Un build Paper écrit `rgl-paper.js` (patchs et événements WebSocket) et `rgl-paper.wasm`. `IWebAssemblyToolchain` est la capacité dédiée ; `ZigToolchain` cible `wasm32-freestanding` avec le Zig déjà géré par RGL. VS Code 0.11.1 reconnaît `.paper` comme HTML et injecte la coloration RGL dans les blocs et interpolations. Voir `Docs/Paper.md`.

## SoA complète (slice B.1, branche `slice-b1-soa-complete`)

- **Vivacité des champs** (`Emit/CppEmitter.Liveness.cs`, sur tout le programme, boxes comprises) : chaque lecture de champ (`IrMemberAccess`, `?.`, champ d'union) note sa chaleur par mold et par chemin (`position.x`). **Chaud** : lu sans branche dans une étape de parcours (gears appelés et lambdas compris) ; **tiède** : lu dans un parcours derrière une branche (`if`, `switch`, ternaire, `and`/`or`, `??`, bras de `match`) ; **froid** : lu ailleurs ; **supprimé** : jamais lu — pas de colonne, le champ se reconstruit à vide (`{}`) à la lecture d'un élément (`_IsDropped`). Les colonnes se rangent chaud, tiède, froid, puis par alignement. Un champ n'est supprimé que si son type se construit à vide (nombres, `bool`, `string`, enum) et si aucune valeur entière du mold n'est observée : `_ObservesChild` donne la liste blanche de ce qui ne fait que transmettre une valeur (argument, retour, conversion, lecture par champ ou index, construction) ; tout le reste — comparaison, texte, JSON, XML, C++ (`IsNative`), `pack`, `switch`, sujet d'un `match` — observe, et un nœud d'IR ajouté plus tard observe par défaut. Un mold avec un champ supprimé reste en colonnes (`_AllHot` exige que toutes soient chaudes).
- **`soa mold`** (`MoldDeclaration.IsSoa`, `MoldSymbol.IsSoa`) : un mold dont chaque champ est un tableau dynamique `[T]` (une colonne), au moins un ; **E153** sinon. En C++ c'est un struct ordinaire de tableaux. **`|S|>`** et **`||S|>`** (`TokenKind.SoaPipe`, `SoaShortestPipe`, `AST/Expressions/SoaEachExpression`, `Binder.SoaRows.cs`) appellent un gear nommé à chaque rang, la valeur de chaque colonne dans le paramètre du même nom (E153 sans colonne de ce nom) ; `|S|>` arrête le programme si les colonnes n'ont pas la même taille, `||S|>` s'arrête à la plus courte (`IrRowCount`, `rows.hpp`). Le résultat est le tableau des valeurs rendues (ou rien). C'est un `IrEach` sur un intervalle de rangs ; les colonnes y sont lues par des pointeurs `__restrict` (`_restrictColumns`). Choix de Claude, à valider : seulement un gear nommé et sans arguments en plus (ni lambda, ni guard, ni emit, ni asynchrone), seulement sur une variable ou un champ de variable, le résultat n'est pas réécrit dans les colonnes, un échec de taille arrête même dans un guard. Pas dans un train (`|>`) ni générique.
- **Vectorisation** : `rgl compile --explain-vectorization` compile en release avec `-Rpass=loop-vectorize` (`ICompilerToolchain.ExplainVectorization`, `Build/VectorizationReport`) sur une copie du C++ dont les `#line` sont des commentaires, puis ramène chaque remarque à la ligne de l'instruction du source : **I003** (vectorisée, largeur) et **W069** (non vectorisée, raisons de Clang traduites quand elles sont connues). Seules les positions du C++ généré comptent, pas celles du runtime.
- **Débordement** (décision « les trois ») : (1) la clé `overflow` du manifeste peut être un objet `{"debug": "checked", "release": "unchecked"}` (`ProjectManifest.OverflowFor`) ; (2) `@checked` et `@unchecked` devant un gear règlent le mode de son corps (`IrGear.Overflow`, `_OverflowOf` ; E125 sur autre chose qu'un gear ou si les deux se contredisent) ; (3) **vérification groupée** automatique : dans un parcours (`IrEach` sans accumulation, sans guard ni rail) dont toutes les étapes sont des lambdas sans effet, `+ - *` n'arrêtent plus à chaque opération (`grouped_add/sub/mul` : calcul en 64 bits jusqu'à 32 bits, intrinsèques au-delà) mais lèvent un drapeau testé une fois après la boucle (`check_grouped_overflow`, position du parcours) ; Clang peut ainsi vectoriser. Les gears nommés appelés par une étape gardent leur vérification immédiate. Un résultat de parcours est écrit par `push_reserved` (place réservée, aucune croissance).
- **`[mold;N]` en colonnes et AoSoA** : un `[mold;N]` suit la même règle que `[mold]` (`_IsSoa` accepte `ArrayKind.Fixed`) et devient `rgl::standard::soa_fixed_array<Layout, N>` (`soa.hpp`) : les colonnes sont rangées dans l'objet (`Layout::fixed_columns<N>`, `T rgl_kI[N]`, aucune allocation), `gather` et `store` du Layout sont génériques sur le conteneur de colonnes. Il se lit, s'écrit en place (`columns()`, `index()`, `set`), se convertit (`from`, `try_from`, `fits`) comme un `fixed_array`. Un `[[mold;N]]` est donc un `array` de ces blocs : l'AoSoA, sans code de plus. Les bornés `[T;N..M]` et `[T+]` restent en tableaux de structs. Tests : `SoaFixedTests`.
- **Pas encore** : `|S|>` en étape de train, avec lambda ou guard ; réécriture du résultat dans les colonnes ; vérification groupée pour les gears nommés et les accumulations ; un banc dédié aux colonnes.

## Disposition mémoire déterministe (slice B.2, branche `slice-b2-memory-layout`)

- **Ordre physique et ordre logique** (`CppEmitter.Molds.cs`, `_PhysicalFields`) : le struct C++ d'un mold range ses champs par **alignement décroissant**, à alignement égal dans l'ordre du mold (tri stable) : aucun padding entre les champs, seulement à la fin. L'ordre du mold reste celui du texte (`{nom: …}`), des valeurs écrites, de l'égalité et des constructeurs. Un mold dont l'ordre physique diffère reçoit un constructeur `constexpr` qui prend les champs dans l'ordre du mold (les membres sont initialisés dans l'ordre où ils sont déclarés) et un constructeur par défaut `= default` (supprimé, comme pour un agrégat, si un champ n'en a pas : l'avertissement `-Wdefaulted-function-deleted` est neutralisé à cet endroit) ; un mold déjà rangé reste un agrégat, `rgl_m_X{a, b}` ne change pas ; un mold à gear de fin (`_LifecycleMembers`) suit la même règle. L'alignement estimé (`_Alignment`, `CppEmitter.Soa.cs`) couvre primitifs, enums, molds (le plus aligné de leurs champs), tuples, unions, nullables et `[T;N]` ; le reste vaut 8 (pointeurs, `string`, tableaux, durées).
- **`static_assert`** (`_LayoutAssertions`) après chaque struct : chaque champ à la position qui suit exactement le précédent (`offsetof`, `-Winvalid-offsetof` neutralisé autour), alignements décroissants (`alignof(decltype(…))`) et, hors cycle de vie, `sizeof` égal à la somme des champs arrondie à l'alignement. Si l'alignement réel d'un type diffère de l'estimation, le build échoue là — c'est un bug du transpileur, vu tout de suite.
- **Niche de `T?`** (`CppEmitter.Niche.cs`, `nullable.hpp`) : quand le compilateur connaît une valeur de `T` que le programme n'utilise jamais, `T?` s'écrit `rgl::standard::niche_nullable<T, Sentinelle>` — la taille de `T`, sans l'indicateur de `std::optional` : un `bool` (2, rangé dans un octet), un enum (la plus grande valeur du type sous-jacent qu'aucune variante n'a, sinon la plus petite), un entier borné (juste au-delà d'une borne). Même interface que `std::optional` (`has_value`, `*`, `value`, `value_or`, `emplace`, `reset`, comparaisons, conversion depuis un `std::optional<T>` que rendent les fonctions du runtime) ; `operator*` rend une valeur, pas une référence ; écrit en texte comme un nullable. Un entier non borné, un flottant, un texte ou un mold gardent `std::optional`. Tests : `tests/rgl.Tests/MemoryLayoutTests.cs`.
- **Pas fait** : les unions restent des `std::variant` (étiquette d'un octet, rangée par la bibliothèque : une union maison ne gagnerait rien de mesurable et casserait `get`/`member`/`widen`/`narrow`), niche dans `string` (son type de stockage `kind_` en laisserait une, mais copie et déplacement de `string` en dépendent) ou dans un mold qui contient un bool.

## Profils de build et positions compactes (slice B.3, branche `slice-b3-memory-builds`)

- **Profils** (`Build/Toolchain/BuildProfile.cs` : un enregistrement `BuildProfile(Name, Kind, CompileFlags, LinkFlags, Overflow)`, plus un enum) : `--debug` (le défaut), `--release`, `--release=size` et `--profile nom`. Trois profils fournis : `debug` (`-O0 -g`, UBSan et le mode **durci** de libc++, `_LIBCPP_HARDENING_MODE_EXTENSIVE` : un index ou un déréférencement invalide dans un conteneur arrête le programme), `release` (`-O2`, sections retirées, `-s`) et `size` (`-Oz`, mêmes sections : environ un quart de moins que `release` sur un petit programme). Un profil du manifeste s'écrit dans la clé `profiles` de `rgl.json` : `"profiles": {"rapide": {"extends": "release", "flags": ["-O3"], "link": [], "overflow": "unchecked"}}` — `extends` (`debug`, `release` ou `size`, `release` par défaut) donne la famille, `flags` et `link` s'ajoutent à ses options, `overflow` règle le débordement (sinon celui du manifeste ; un profil qui optimise prend celui de `release`) ; un nom en minuscules, chiffres, `-` `_`, jamais celui d'un profil fourni. Le dossier de sortie est `out/<nom>`, le cache des objets du runtime est rangé par nom et empreinte (`BuildProfile.Key`, options comprises). Un nom inconnu est une erreur qui liste les profils ; deux options de profil dans une commande aussi. `CliRunner._ResolveProfile`, `ProjectManifest.ReadProfiles`/`OverflowFor(BuildProfile)`. Tests : `tests/rgl.Tests/BuildProfileTests.cs`. LTO ne se lie pas sous MinGW avec Zig 0.17 (voir plus haut) et PGO demande des outils (`llvm-profdata`) que Zig ne fournit pas : un profil du manifeste peut tenter `-flto` (sous Linux), rien n'est promis. Les sanitizers : UBSan reste celui du debug ; AddressSanitizer n'existe pas pour MinGW.
- **Positions compactes** (`Emit/CppEmitter.Rows.cs`, `_Position`, `runtime/include/rgl/standard/position.hpp`) : une opération entière contrôlée (`checked_*`, `wrapping_div/rem`) reçoit sa position dans une constante `rgl::standard::position` de 32 bits — fichier (6 bits), ligne (18), colonne (8), chacun ramené au maximum de son champ — au lieu du texte `"main.rgl:44:19"` : un immédiat, sans adresse ni octets de chaîne (environ 17 octets de moins par opération : 21 Ko sur 1 200 opérations). Le programme définit `rgl::standard::position_files` (les noms des fichiers, `nullptr` à la fin) quand il écrit une position ; l'arrêt la décode (`detail::position_text`). Les fonctions d'`arithmetic.hpp` prennent le type de la position en paramètre de patron (`W`) : le texte reste accepté (les tests du runtime). Pas encore : les autres positions (`at(i, where)`, `push`, casts, bornes) restent des textes.
- **Pas fait** : LTO/PGO comme profils fournis.

- **Allocateurs, pool et arènes** (`memory.hpp`, `pool.hpp`, `arena.hpp`, `Emit/CppEmitter.Arena.cs`, `Binding/Binder.Arena.cs`) : une `AbiAllocator` (trois pointeurs de fonction qui reçoivent l'allocateur en premier argument, donc à état, plus `scoped`) ; `default_allocator()` rend l'**allocateur ambiant** du thread (celui de l'`allocator_scope` le plus récent, sinon `heap_allocator()`, le système, que le runtime utilise pour son propre état et que `function` utilise) ; un tableau, un texte ou un dictionnaire **fixe son allocateur à sa construction** et s'en sert toute sa vie. **Pool** : `ArenaPool.set(valeur)` (`IrPoolValue`, `_BindPoolValue`) évalue `valeur` sous le pool (`pool_allocator()` : classes de tailles de 16 à 2 048 octets, listes libres par thread, en-tête de 8 octets, jamais rendu au système) ; même type que `valeur` (un entier reste un entier) ; une valeur qui n'est qu'une variable n'est pas reconstruite ; pas de règle d'échappement (un bloc rendu retourne à la liste de sa classe). **Arène** : `arena { … }` ou `arena(octets) { … }` (`BlockStatement.IsArena`, `IrBlock.IsArena`) ouvre `rgl::standard::arena_scope` : une arène (segments chaînés de 64 Ko, doublant jusqu'à 16 Mo, premier segment réutilisé d'un bloc à l'autre, `reset` à la fin, par `return`/`fail`/`break` comme par la fin normale) devient l'allocateur ambiant, y compris pour les gears appelés. **Sûreté sans analyse d'échappement** : l'allocateur d'une arène est `scoped`, et ce qui vient d'une arène n'est jamais repris tel quel ailleurs que dans cette arène — une copie ou un déplacement (`array`, `mstring`, `string`) crée sur le tas quand l'arène de la source n'est pas l'allocateur ambiant, une affectation dont la source est dans une arène qui n'est pas celle de la destination recopie dans la destination (le texte d'arène n'est jamais partagé par une affectation), un tableau construit ses éléments sous son propre allocateur (`_construct_each`) et `function` construit ce qu'elle capture sous le tas. Les retours élidés (`return x;` construit la valeur dans l'appelant) sont refermés par `rgl::standard::detach` (tas ambiant pendant la construction), que l'émetteur écrit autour de la valeur d'un `return`, `done` ou `fail` dans un bloc arena (`_Detached`, seulement pour un type qui peut tenir de la mémoire). **E154** : une attente (`await`, l'attente d'un `@sync`), l'appel d'un gear `@async`/`@fire`/`@sync`, une taille qui n'est pas un entier connu à la compilation, dans une arène ; une attente dans `ArenaPool.set(…)`. Mesure (20 000 frames de trois tableaux et d'un tableau de textes, release) : 316 ms sans, 156 ms avec une arène, 156 ms avec le pool. Tests : `ArenaTests`, `runtime/tests/arena_tests.cpp`, golden `Golden/parser/arena`. Pas encore : `ArenaPool.set` d'une variable qui reconstruirait sa valeur, un banc dédié, les dictionnaires et colonnes SoA restent allocateurs du tableau sous-jacent (ils suivent), les temporaires de pipeline par analyse d'échappement (reporté : un pipeline fusionne déjà ses boucles).

## Accumulateur déplacé (slice B.4b, première tranche, branche `slice-b4b-moves`)

- Dans une accumulation `|+>`, quand l'étape est une lambda écrite sur place dont le premier paramètre (l'accumulateur) n'est pas `mut` et possède de la mémoire (`LastUses.IsWorthMoving` : tableau, dictionnaire, texte, tuple ou mold qui en contient), l'émetteur la passe **par valeur** et l'appelle avec `std::move(accumulateur)` (`CppEmitter._ConsumesAccumulator`, `_LambdaCode(…, consumedFirst: true)`). Le `return acc;` d'un paramètre par valeur est alors un déplacement implicite : l'étape qui laisse l'accumulateur inchangé ne recopie plus son tableau à chaque élément. L'accumulateur est réaffecté du résultat juste après l'appel, rien ne le relit entre-temps. Pas encore : un gear ou un guard nommé comme étape (ses paramètres restent `const&`), une accumulation dans un guard (`_CallText`).
- Mesure (compteurs, release) : `chaines` 22 037 → 2 copies de tableaux, 5,6 M → 0 élément copié, 35 836 → 13 829 allocations, 391 → 84 Mo ; le temps ne bouge presque pas (≈ 590 → 570 ms) : il est dominé ailleurs (`string.length`, `substring`, `at(i)` sont O(n) dans la std) et le reste des allocations vient de `[...acc, x]` (B.4c). `json` (600 000 copies, SoA : chaque élément lu est reconstruit par `gather`, avec son tableau `tags`) n'est pas touché : à traiter avec les lectures d'éléments SoA. Tests : `tests/rgl.Tests/Emit/MoveTests.cs`.

## `[...acc, x]` repris et dictionnaire par lots (slice B.4c, branche `slice-b4c-algorithmique`)

- **Décisions de l'utilisateur** : compteurs de références d'`array` et de `dictionary` atomiques seulement pour ce qui traverse `@task` (le partage avec compteur n'est pas encore écrit : voir plus bas) ; `[K:V]` construit par lots.
- **Tableau étalé repris** : `[...a, x, …]` s'écrit `rgl::standard::make_array_from<E>(std::move(a), x, …)` (`runtime/include/rgl/standard/array.hpp`) quand le premier morceau est un tableau étalé que rien ne relit ensuite : le bloc de `a` est repris tel quel et les autres morceaux s'ajoutent à sa suite (croissance ×1,5), donc une boucle d'ajouts est linéaire et non plus quadratique. `Emit/LastUses.cs` décide (`Result.Spreads`, `CppEmitter._spreadMoves`) : le premier morceau est une « place » — une variable locale non constante ou le paramètre d'accumulateur que `LastUses.ConsumesAccumulator` reçoit par valeur (B.4b), éventuellement suivie d'une chaîne de champs de mold et d'éléments de tuple (`state.Item1`) —, hors boucle, lambda ou bras de match, et aucune mention ultérieure de la même racine ne recouvre son chemin (un autre champ du même tuple ne gêne pas ; relire `a`, `a.length` ou `a[0]` dans un morceau suivant, si). La mention d'une variable garde son comportement précédent (dernière mention) ; celles des paramètres et des chemins sont nouvelles (`_mentions`). Émis seulement pour un `[T]` dynamique non SoA dont la source a le même type d'élément ; les morceaux suivants étalés restent copiés (`spread(...)`). Tests : `tests/rgl.Tests/Emit/SpreadMoveTests.cs`.
- **Dictionnaire par lots** (`runtime/include/rgl/standard/dictionary.hpp`) : les clés ajoutées par `add` vont dans un petit tampon trié (`_pending_keys`/`_pending_values`), versé dans les tableaux principaux par une fusion quand sa taille au carré dépasse celle des principaux plus 256 (`_flush`), ou avant une lecture qui a besoin de tout l'ordre (parcours, `keys`, `values`, `==`, `put`, `without`) ; une lecture d'une clé cherche dans les deux. Un `[K:V]` construit par n ajouts coûte environ n·√n au lieu de n² ; les membres sont `mutable` : **un dictionnaire n'est lu que par un thread à la fois** (une tâche reçoit une copie). `array::allocator()` est public pour que le versement garde l'allocateur. Banc `bench/dictionnaire` (100 000 ajouts brouillés puis relus) : ≈ 275 → ≈ 70 ms de travail ; `chaines` : 13 829 → 12 864 allocations (le reste vient des gabarits qui reconstruisent le texte : B.6). Tests : `runtime/tests/array_tests.cpp` (`test_dictionary_batches`).
- **Pas fait** : le partage avec compteur et copie à l'écriture de `array`/`dictionary` (la copie reste profonde ; `make_array_from` couvre le cas d'un tableau qu'on ne relit plus) ; un compteur non atomique distinct de l'atomique pour `string`/`function`.

## Récursion terminale en boucle (slice B.4d, branche `slice-b4d-locales`)

- **Récursion terminale** (`Emit/TailCalls.cs`, `CppEmitter._tailGears`) : un gear dont chaque appel à lui-même est un `return f(…);` direct s'écrit en C++ comme une boucle `for (;;) { … }` : un appel terminal (`_TailCall`) calcule tous les nouveaux arguments dans des temporaires avec les valeurs du tour, les déplace dans les paramètres (un argument qui est le paramètre lui-même ne change rien) puis fait `continue;`. **Pas de `recursion_guard`** : la limite de profondeur ne s'applique plus à un tel gear (une récursion terminale de millions de tours ne s'arrête plus à 200, ni ne dépasse la pile) ; le garde empêchait aussi Clang de la transformer lui-même. Ses paramètres sont **passés par valeur** (`_Signature`) : une variable de boucle ne peut pas être une `const&` ; un tableau passé tel quel au premier appel est donc copié une fois, jamais à chaque tour. Retenu seulement si : gear ordinaire (ni guard, emit, train, asynchrone, natif), au moins un appel terminal, aucun autre appel à lui-même (ni dans une lambda, ni dans une valeur de gear), aucun appel d'un autre gear récursif (une récursion mutuelle garde ses gardes), pas de `@tap`, de valeur par défaut, de `params`, de paramètre `mut`, à cycle de vie ou pointeur, retour non `void`. Mesure : banc `bench/terminale` (100 millions de tours, limite par défaut) : avant, arrêt à 200 appels (code 127) ; après, ≈ 40-60 ms. Tests : `tests/rgl.Tests/Emit/TailCallTests.cs`.
- **Essayé et abandonné, faute de gain mesuré** (critère d'arrêt de B.4) : (1) des faits d'intervalle pour retirer `checked_add`/`checked_sub` prouvés inutiles (`n - 1` après `if (n < 2) { return n; }`) : en release Clang prouve déjà ces cas (`fib` : 160 → 160 ms), en debug ≈ 10 % seulement ; (2) `[[gnu::cold, gnu::noinline]]` sur les fonctions d'arrêt du runtime et `[[unlikely]]` sur les contrôles : exécutables de même taille au Ko près et mêmes temps sur cinq bancs. Ce que coûtent encore `fib` (160 ms contre ≈ 55 ms avec `"recursion": "infinite"` et `"overflow": "unchecked"`) : le garde de récursion (≈ 50 ms, un compteur par thread) et le contrôle de débordement qui empêche Clang de transformer un des deux appels en boucle ; ni l'un ni l'autre ne se supprime sans changer le sens de la limite de profondeur ou du mode `checked`.

## Fusion de parcours et rapport d'optimisation (slice B.4e, branche `slice-b4e-fusion`)

- **Fusion** (`Emit/LoopFusion.cs`, appelée aux quatre endroits qui écrivent une liste d'instructions : corps de gear, bloc, lambda) : deux déclarations qui se suivent, dont la seconde parcourt le tableau que la première construit par un parcours (`[int] a: xs ||> f; [int] b: a ||> g;`), deviennent un seul `IrEach` (source du premier, étapes concaténées, accumulation du second) : le tableau intermédiaire n'existe plus, et une chaîne de trois ou plus se réunit pas à pas. Conditions : les déclarations sont adjacentes ; la variable intermédiaire n'est pas `mut`, est un `[T]` dynamique, et n'est lue que comme source du second parcours (aucune mention plus loin, lambdas comprises) ; aucune étape n'a d'effet (`IrEffects.HasEffects`), de guard, de rail ni ne modifie sur place ; l'accumulation du second n'a ni effet, ni guard, ni rail, ni `done valeur` (qui l'arrêterait avant la fin du premier parcours). **Seule différence observable** : si les deux parcours s'arrêtaient sur un dépassement ou un index hors limites, le premier élément fautif n'est plus forcément celui du premier parcours (les deux programmes s'arrêtent). Mesure : `bench/fusion` (trois parcours, vingt millions d'entiers) ≈ 49 → ≈ 25 ms, comme la chaîne écrite en une seule instruction. Tests : `tests/rgl.Tests/Emit/LoopFusionTests.cs`.
- **Rapport** : `rgl compile --explain-optimizations` (`CommandLine.ExplainOptimizations`, `BuildOutput.Optimizations`) transpile sans compiler et rend en diagnostics `OptimizationNote` (`CppProgram.Notes`, rempli par l'émetteur : `_Note`, `_AddNote`) : **I004** pour ce qui est fait (deux parcours fondus, accumulateur déplacé, `[...a, …]` repris, récursion terminale écrite en boucle) et **W070** pour ce qui est refusé, avec la raison (parcours non fondus : variable relue, effet, `mut`, guard, rail, `done valeur` ; récursion qui reste récursion : `TailCalls.Reason`). Les notices I001 de conversion s'y mêlent comme ailleurs. Tests : `tests/rgl.Tests/OptimizationReportTests.cs`.
- Pas fait : le rapport ne dit pas encore les contrôles supprimés ni les copies profondes restantes (B.4b), ni le passage des paramètres ; la fusion d'un parcours avec un `return`/une expression plutôt qu'une déclaration, ou de parcours non adjacents.

## Chaînes en temps linéaire (slice B.5, branche `slice-b5-chaines`)

- **Compte de caractères en cache** (`runtime/include/rgl/standard/string.hpp`, `src/string.cpp`) : le bloc du tas d'un `string` (`Control`) porte, à côté du compteur de références, `characters`, le nombre de caractères Unicode, calculé à la première demande de `length()` (`npos` tant que non fait) et **partagé par toutes les copies** (atomique relaxé ; le texte d'un bloc ne change jamais). `string::is_ascii()` (`length() == size()`) dit qu'aucun caractère n'est multi-octet : `character(rang)` — donc `s[i]` — rend alors l'octet sans rien parcourir. Un texte petit (≤ 22 octets) ou une vue (littéral long) se recompte à chaque demande (peu d'octets, ou rare). Le bloc du tas pèse 8 octets de plus. Un texte non ASCII garde `s[i]` en O(rang) : écrire un parcours caractère par caractère d'un texte accentué reste quadratique.
- **Opérations en un passage** (`runtime/include/rgl/standard/text.hpp`, en-tête seul, espace de noms `rgl::standard::text`) : `substring` (rangs négatifs depuis la fin, ramenés aux bords), `index_of`, `last_index_of`, `split`, `join`, `replace`, `upper`, `lower`, `repeat`, `reverse`. Les rangs sont des caractères, les recherches se font sur les octets (exact en UTF-8 valide), le résultat est construit d'un coup (`string::with_size` : une allocation, aucune jusqu'à 22 octets). Mêmes résultats que les gears RGL qu'elles remplacent (motif vide : `indexOf` 0, `lastIndexOf` la longueur, `split` le texte entier, `replace` le texte inchangé ; majuscules ASCII seulement).
- **La std** (`std/extentions/strings_ext.forge`, `collections_ext.forge`) : `substring`, `indexOf`, `lastIndexOf`, `repeat`, `reverse`, `toUpper`, `toLower`, `split`, `replace` appellent des gears privés `_textSubstring`… (`@trusted`, bloc `cpp` qui inclut `text.hpp` ; `@trusted` n'est pas permis **dans** un `extend`, d'où des gears de premier niveau documentés fr/en) et `join` d'un `[string]` passe par `_joinText` (`if (T is string)`). Les autres gears de chaînes (`startsWith`, `trim*`, `padStart`…) restent en RGL et profitent de `substring`/`s[i]` en O(1).
- **Mesure** : banc `chaines` (maintenant 2 000 lignes) 18 s → ≈ 19 ms ; 20 000 lignes (525 Ko) ≈ 45 ms, avec ou sans accents. Tests : `tests/rgl.Tests/StdStringsTests.cs` (rangs en caractères, emojis, découpe, jonction, remplacement, majuscules, inversion, 20 000 lignes), `runtime/tests/text_tests.cpp`.
- Pas fait : `startsWith`/`endsWith`/`trim*`/`padStart`/`format` en primitives (ils passent déjà par des gears en O(1) ou O(longueur du motif) sur l'ASCII) ; index de sauts pour le rang dans un texte non ASCII ; `string::substr` du runtime compte toujours des octets (le gear RGL compte des caractères) ; majuscules Unicode ; un gabarit `` `{acc}{x}` `` dans une boucle reconstruit encore son texte à chaque tour (un ajout en place demanderait un `string` extensible partagé).

## Grosses constantes en tables (slice B.6, branche `slice-b6-datasets`, première partie)

- **Tables constexpr** (`Emit/CppEmitter.Tables.cs`, `_TryTable`, appelée avant l'écriture d'une déclaration de premier niveau) : une constante de fichier non déjà `constexpr` dont la valeur est (1) un tableau dynamique `[T]` de `TableThreshold` (64) éléments ou plus, tous connus à la compilation (`ConstantFolder.Fold` non nul : nombres, textes, molds de valeurs connues — donc les datasets, qui sont des constantes de precast) ou (2) un dictionnaire de 64 entrées ou plus dont les clés et les valeurs sont connues et les clés des entiers ou des textes, s'écrit `static constexpr fixed_array<E, N> rgl_dK = …;` puis `A::from(rgl_dK, where)` (tableau, `soa_array` compris), ou `static constexpr std::pair<K, V> rgl_dK[N] = {…};` puis `dictionary<K, V>::from_sorted(rgl_dK, N)` (`dictionary.hpp`) : les données sont dans l'exécutable, le programme ne fait qu'une boucle de recopie au démarrage. Le compilateur **range** lui-même les paires du dictionnaire (`_CompareKeys` : entiers par valeur, textes octet par octet en UTF-8, comme `key_less` du runtime — un `é` passe après un `z`) et abandonne la table (écriture ordinaire) pour une clé non comparable ou en double. Mesure : `constantes-demarrage` 37 → 5,4 s de compilation, 1,24 → 0,65 Mo ; nouveau banc `dataset` (5 000 entrées, `bench/generer-dataset.py`) 21 → 5,3 s, 1,37 → 0,63 Mo. Tests : `tests/rgl.Tests/Emit/TableTests.cs`.
- Pas encore (B.6) : table mutable, extension d'un dataset depuis un autre fichier (mods), `get()` qui lit une colonne sans reconstruire l'élément (à mesurer : Clang supprime peut-être déjà le rassemblement), `[T;N]` constexpr pour une table fixe.

**B.6, suite : mods et table mutable** (décisions de l'utilisateur du 2026-11-05 : identifiants **positionnels, ajout seulement** ; extension **à la compilation** par un fichier).
- **`extend dataset Moves { braise: {name: 'Braise', power: 9}, … }`** (`AST/Datasets/DatasetExtension`, `Parser._AtDatasetExtension`/`_ParseDatasetExtension`) : un fichier qui importe celui qui déclare le dataset — ou un `forge: extend`, chargé d'office, pour un DLC qu'il suffit de poser dans le projet — ajoute des entrées. `SourceGraph._MergeDatasetExtensions` les fond dans la déclaration avant la liaison : elles suivent celles du fichier qui déclare le dataset, dans l'ordre où les fichiers se lient, donc **les identifiants du jeu de base ne bougent jamais** ; les entrées se lient là où le dataset est déclaré (pas de nom visible seulement du mod). ## Extension VS Code 0.13.0 : création de mold, obsolète barré, navigation, tâches

- **Champs d'un mold à la création** (`Lsp/CompletionProvider.Molds.cs`, `_MoldFields`, appelée avant `_Everything`) : le curseur est à la place d'un nom de champ quand le dernier signe avant le mot est `{` ou `,` ; le mot est remplacé par un nom provisoire (`Placeholder`, comme `_Members`) pour que la valeur existe dans l'arbre même inachevée, puis le `MoldExpression` qui contient ce nom donne le type attendu (`_ExpectedType` : le type écrit après `new`, sinon celui de la déclaration typée, de l'affectation, du paramètre dont la valeur est l'argument d'un gear, du retour, du champ d'un mold englobant — récursif —, de l'élément d'un tableau attendu). ## Outillage (slice V1.1) : formateur officiel

Le formateur (`Lsp/Formatter.cs`) n'a **aucun réglage** : quatre espaces (`Formatter.IndentUnit`), les options `tabSize`/`insertSpaces` de l'éditeur sont ignorées. `Formatter.FormatText(chemin, texte)` met un texte entier en forme (sans projet). **`rgl format [chemin…] [--check]`** (`Cli/FormatCommand.cs`) l'applique aux `.rgl` et `.forge` des fichiers et dossiers donnés (le dossier courant par défaut ; dossiers cachés, `out` et `node_modules` écartés ; `.paper` non touchés) ; un fichier qui ne se lit pas jusqu'au bout (UTF-8 invalide, erreur de syntaxe) n'est pas touché et fait échouer la commande ; le BOM et les fins de ligne sont gardés ; `--check` n'écrit rien et échoue s'il reste des fichiers à mettre en forme. Tests : `FormatterTests`, `FormatCommandTests`. Les textes engendrés d.un fichier de données (`import json`, `import xml`, dataset `from`) passent par `Formatter.FormatText` dans `SourceGraph` ; les liaisons C et les descriptors engendrés n.y passent pas.

**Indications de l'éditeur** (`DocumentReport.Hints`, `DocumentAnalysis._Hints`, requête `textDocument/inlayHint`) : en plus du `mut` devant un argument, le type déduit de chaque `var` s'écrit grisé après son nom (`var a: 4;` → `: int`, genre « type » ; un type écrit n'en reçoit pas) et chaque point où un gear asynchrone se suspend (`await`, « ⏸ peut se suspendre ») ou se bloque (attente d'un gear `@sync`, « ⏳ bloque jusqu'à la fin ») reçoit un indice devant l'expression.
